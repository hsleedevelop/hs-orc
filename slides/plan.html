S0

파이프라인 먼저 — 코드보다 게이트

  • 프로젝트 초기화. TypeScript(strict). Core는 런타임 중립으로 쓴다
  • 레이어 경계를 디렉터리로 고정: core/ adapters/ shell/ data/. core/가 shell/을 import하면 lint 에러
  • CI 또는 pre-commit: tsc --noEmit + lint + test. no-floating-promises를 error로
  • pre-commit 시크릿 스캔 — CURSOR_API_KEY 같은 값이 커밋되지 않게
  • matrix.json 생성 스크립트 — 원본 HTML의 rows/profiles를 파싱
완료 판정

일부러 타입 에러를 넣으면 게이트가 실패하고, 고치면 통과한다. 설정만 있고 게이트가 없으면 완료가 아니다.

S1

뼈대 e2e — 여기서 멈추고 보고한다

범위

작업 문자열 1개 → 11행 중 1행 분류 → primary 슬롯만 배정 → 엔진 비대화 실행 → stdout 패스스루

없는 것

UI · reviewer · 로그 · 비용 · 진행 방식 · 증거 수집

완료 판정 — 3건이 서로 다른 엔진으로

입력 예기대 배정
"이 타입 에러 고쳐줘"Luna·medium → codex
"이 기능 새로 구현해줘"Sol·high → codex
"이 아키텍처 검토해줘"Fable·high → claude
위험

실제 모델 id를 CLI가 받는 형태로 확정해야 한다. codex -m이 받는 정확한 문자열을 실행으로 확인하고 engines.json에 박는다. 추측하지 않는다.

S2

엔진 어댑터

  • buildArgv() — 세 엔진 argv 생성. codex는 exec 서브커맨드(-p 아님)
  • effort 검증 — 정규 어휘 밖이면 던진다. claude가 조용히 기본값으로 돈다는 것이 실측 확인됐으므로 여기가 유일한 방어선
  • Cursor 어댑터 — effort가 모델 id 접미사. 바이너리는 cursor-cli → 없으면 cursor-agent 폴백
  • supports() — Astra·Haiku는 Cursor에 없다. 지원하지 않는 조합은 명시적 실패
  • stream-json 파싱 — 중첩 try. 원본 stdout/stderr는 실행별 보존
  • 취소·타임아웃 — 프로세스 그룹 단위 종료
완료 판정 · 위험

단위(기대 argv, 잘못된 effort가 던짐, Astra+cursor 실패) + 통합(세 CLI 실제 1회) + 취소 테스트(좀비 없음). 좀비 프로세스는 비용이 계속 나간다 — 이 테스트를 빼지 않는다.

S3

라우팅 엔진

  • Gatekeeper — §1 하한선 6개. 걸리면 배정하지 않고 종료. 하한선이 배정보다 앞이다
  • Assigner — 두 슬롯 배정. INV-1을 타입 수준에서 강제할 수 있으면 그렇게, 아니면 생성 시 검사 후 실패
  • 비용 산정 — primary + reviewer 합산. AA 측정치임을 값과 함께 운반
  • 상향 사다리 — L1→L5. 근거 보강 → effort → 모델 → reviewer 순서 강제, L5 직행 경로 금지
  • "해당 없음" — 사용자에게 올린다. 기본 배정을 만들지 않는다
  • 분류기 개선 — 규칙으로 부족하면 저비용 모델로 분류만. 분류에 Fable을 쓰지 않는다
완료 판정

11행 테이블 테스트 · 원본 HTML 대조 · INV-1 위반 시도 실패 · 하한선 입력이 프로세스 spawn 0회 · 상향이 사다리를 건너뛰지 않음

S4

진행 방식 3종

공통 인프라 먼저 — 사이클 단위 기록(근거·변경·검증), 최대 시도 카운터, 누적 비용 추적, 상한 도달 시 에스컬레이션. 세 방식이 공유한다.

S4-a

/pingpong

턴 단위. 사용자 입력 대기. 방향 수정·배정 변경·중단 가능. 최대 턴 제한 없음, 누적 비용 상시 표시.

S4-b

/loop

7개 구성요소 분리. Evaluator에 reviewer 슬롯 모델. 최대 반복 수 없이는 구현하지 않는다.

S4-c

/graph

노드별 독립 배정. 실행 전 순환 검출. 병렬은 쓰기 비겹침 확인 시만. 전파 규칙 3종.

완료 판정 — 순서가 거꾸로다

세 방식 각각이 상한에 걸려 정상 중단되는 것을 테스트로 보인다. 정상 완료보다 이 경로를 먼저 검증한다. 무한 루프는 비용이 직접 나간다 — 상한 없는 방식은 머지하지 않는다.

  • 정상 비즈니스 상태를 에러로 올리지 않는다. catch 후 무동작 금지
