# hs-orchestrator — 구현 계획

- 버전: v0.1 (초안)
- 작성일: 2026-09-20
- 선행 문서: `docs/PRD.md`, `docs/SPEC.md`

## 원칙

- **가장 작은 end-to-end부터 완성하고, 검증된 상태 위에 확장한다.** 추상화를 먼저 세우지 않는다.
- 각 단계는 앞 단계가 **실제로 도는 것**을 확인한 뒤 시작한다.
- 게이트(`type-check → lint → test`)는 단계 종료 시 1회. 파일마다 반복하지 않는다.
- v1 Core는 UI를 모른다. v2에서 재작성이 필요하면 v1 설계가 틀린 것이다.

## S0 — 파이프라인 먼저

코드보다 게이트를 먼저 세운다.

1. 프로젝트 초기화. 스택은 TypeScript(strict) 기준. 런타임·TUI 프레임워크는 S5에서 확정하되, Core는 런타임 중립으로 쓴다.
2. 레이어 경계를 디렉터리로 고정: `core/` `adapters/` `shell/` `data/`. `core/`가 `shell/`을 import하면 lint 에러.
3. CI(또는 pre-commit): `tsc --noEmit` + lint + test. `react-hooks/exhaustive-deps`는 해당 없음, 대신 `no-floating-promises`를 error로.
4. pre-commit 시크릿 스캔(gitleaks 등). `CURSOR_API_KEY` 같은 값이 커밋되지 않게 한다.
5. `matrix.json` 생성 스크립트: 원본 HTML의 `rows`/`profiles`를 파싱해 JSON으로 뽑는다. 첫 줄에 `// GENERATED — 소스: <경로>`.

**완료 판정**: 일부러 타입 에러를 넣으면 게이트가 실패하고, 고치면 통과한다. 설정만 있고 게이트가 없으면 완료가 아니다.

**위험**: 이 단계를 건너뛰고 S1로 가면 나중에 레이어가 섞인다. ebc 3저장소 실측에서 확인된 패턴이다.

## S1 — 뼈대 e2e

**여기서 멈추고 보고한다.** 이 단계가 안 돌면 설계 문제이지 다음 단계로 덮을 문제가 아니다.

범위: 작업 문자열 1개를 CLI 인자로 받아 → 11행 중 1행으로 분류 → **primary 슬롯만** 배정 → 해당 엔진을 비대화로 실행 → stdout 그대로 출력.

없는 것: UI, reviewer, 로그, 비용, 진행 방식, 증거 수집.

1. 분류기 최소 구현. 규칙 기반으로 시작한다(키워드 + 사용자 수동 선택). LLM 분류는 S3에서 필요하면 붙인다.
2. `matrix.json`에서 primary 모델·effort를 읽는다.
3. 모델 → 엔진 매핑 최소판(`SPEC §3.2` 기본 엔진 열만).
4. 프로세스 실행. 스트림 파싱 없이 stdout 패스스루.

**완료 판정**: 아래 3건이 서로 다른 엔진·모델·effort로 실제 프로세스를 띄운다.

| 입력 예 | 기대 배정 | 기대 명령 |
|---|---|---|
| "이 타입 에러 고쳐줘" | Luna·medium | `codex exec … -m <luna> -c model_reasoning_effort="medium"` |
| "이 기능 새로 구현해줘" | Sol·high | `codex exec … -c model_reasoning_effort="high"` |
| "이 아키텍처 설계 검토해줘" | Fable·high | `claude -p … --model <fable> --effort high` |

**위험**: 실제 모델 id(`<luna>` 등)를 CLI가 받는 형태로 확정해야 한다. `codex -m`이 받는 정확한 문자열을 S1에서 확인하고 `engines.json`에 박는다. 추측하지 말고 실행으로 확인한다.

## S2 — 엔진 어댑터

`EngineAdapter` 인터페이스(SPEC §3.1) 뒤로 세 엔진을 넣는다. **이 단계 이후 CLI 플래그 문자열은 어댑터 밖에서 보이지 않는다.**

1. `buildArgv()` — 세 엔진의 argv 생성. `codex`는 `exec` 서브커맨드(`-p` 아님).
2. **effort 검증** — 정규 어휘(`low|medium|high|xhigh|max`) 밖이면 **던진다**. `claude`가 잘못된 값을 경고만 내고 기본값으로 돈다는 것이 실측 확인됐으므로(SPEC §0.1-2) 여기가 유일한 방어선이다.
3. Cursor 어댑터 — effort가 모델 id 접미사다. `gpt-5.6-sol-xhigh` 형태로 조립하고 `-thinking`/`-fast` 변형 정책을 `engines.json`에서 읽는다. 바이너리는 `cursor-cli` → 없으면 `cursor-agent` 폴백.
4. `supports()` — 모델별 가용성. **Astra·Haiku는 Cursor에 없다**(실측). 지원하지 않는 조합 요청은 명시적 실패이며, 가장 가까운 모델로 말없이 바꾸지 않는다.
5. `--output-format stream-json` 파싱. **중첩 try**로 감싸 한 줄 파싱 실패가 실행 전체를 죽이지 않게 한다. 원본 stdout/stderr는 실행별로 보존한다.
6. 취소·타임아웃. 프로세스 그룹 단위 종료.

**완료 판정**
- 어댑터 단위 테스트: 세 엔진 기대 argv, 잘못된 effort가 던짐, Astra+cursor가 실패함
- 통합: 세 CLI로 짧은 실제 프롬프트 1회씩 성공
- 취소 테스트: 실행 중 취소 후 자식 프로세스가 남지 않음 (좀비 없음)

**위험**: 좀비 프로세스는 비용이 계속 나간다. 취소 테스트를 빼지 않는다.

## S3 — 라우팅 엔진

파이프라인 전체(SPEC §4)를 완성한다.

1. **Gatekeeper** — `/delegation-router` §1 하한선 6개 점검. 걸리면 배정하지 않고 종료한다. **순서가 핵심이다**: 하한선이 배정보다 앞이다.
2. **Assigner** — 두 슬롯 배정. `INV-1` 교차 벤더 검사를 타입 수준에서 강제할 수 있으면 그렇게 하고, 아니면 생성 시 검사 후 실패.
3. **비용 산정** — primary + reviewer 합산. AA 측정치임을 값과 함께 운반한다.
4. **상향 사다리** — L1→L5. 상향 요청 시 `근거 보강 → effort → 모델 → reviewer` 순서를 강제하고, L5 직행 경로를 만들지 않는다.
5. **"해당 없음"** — 사용자에게 올린다. 기본 배정을 만들지 않는다.
6. 분류기 개선 — 규칙으로 부족하면 저비용 모델(Haiku·low 또는 Luna·low)로 분류만 시킨다. 분류에 Fable을 쓰지 않는다.

**완료 판정**
- 11행 전부 테이블 테스트 통과, `matrix.json`이 원본 HTML과 대조 테스트 통과
- INV-1 위반 조합을 만들려는 시도가 실패
- 하한선에 걸리는 입력이 엔진을 띄우지 않음 (프로세스 spawn 0회 확인)
- 상향 요청이 사다리를 건너뛰지 않음

**위험**: 매트릭스를 단일 엔진 선택기로 축소하는 것. reviewer 슬롯이 살아 있는지 매 커밋에서 확인한다.

## S4 — 진행 방식 3종

**공통 인프라 먼저**: 사이클 단위 기록(근거·변경·검증), 최대 시도 카운터, 누적 비용 추적, 상한 도달 시 에스컬레이션. 세 방식이 이것을 공유한다.

### S4-a `/pingpong` — 대화형
턴 단위 진행. 턴 종료 시 결과·다음 제안을 제시하고 **사용자 입력을 기다린다.** 사용자는 방향 수정·배정 변경·중단이 가능하다. 최대 턴 제한 없음(매 턴 사용자 승인). 누적 비용 상시 표시.

### S4-b `/loop` — loop-engineering
Goal / Planner / Executor / Evaluator / Critic / Recovery / Stop을 **분리된 구성요소**로 구현한다. Evaluator에는 reviewer 슬롯 모델을 쓴다 — 독립 리뷰가 루프 안에서 실현되는 자리다.
**최대 반복 수 없이는 구현하지 않는다.** 누적 비용 상한 도달 시 강제 중단.
> 미결: 내장 `/loop` 스킬 활용 여부. 기본안은 자체 구현(SPEC §6.2).

### S4-c `/graph` — graph-engineering
노드별 독립 분류·배정. **순환 검출은 실행 전 필수**. 병렬 실행은 **쓰기 대상 파일 비겹침이 확인된 경우만**, 불확실하면 순차로 떨어뜨린다. 부분 실패 전파 규칙(`fail-fast` / `skip-dependents` / `continue`)을 노드마다 선언. 최대 노드 수와 누적 비용 상한 강제.

**완료 판정**: 세 방식 각각이 상한(반복 수 / 노드 수 / 비용)에 걸려 **정상 중단**되는 것을 테스트로 보인다. 정상 완료보다 이 경로를 먼저 검증한다.

**위험**: 무한 루프는 비용이 직접 나간다. 상한 없는 방식은 머지하지 않는다.

## S5 — TUI 셸

S1~S4가 전부 헤드리스로 돈 뒤에 붙인다.

1. TUI 프레임워크 선택. 이 시점의 Core는 UI에 의존하지 않으므로 교체 비용이 낮다.
2. 화면 5개 (SPEC §7): Run / Tasks / Dashboard / Sessions / Reviews.
3. **비용은 실행 전에 보인다.** "AA 벤치마크 측정치, 실제 지출 아님" 표기 포함.
4. 근거 등급 배지 분리 표시. TB4 0.3pp 차이로 우열 표시하지 않는다.
5. Sessions: `codex agents` + `claude agents` 통합.
6. Reviews: `gh-axi` 우선, `gh` 폴백.
7. 디버그 화면을 프로덕션 빌드에 포함. 화면 타이틀에 환경 + 버전.

**완료 판정**: 실제 작업 1건이 입력 → 분류 → 배정·비용 확인 → 승인 → 실행 → 증거 수집까지 화면에서 통과한다.

## S6 — 관찰가능성

1. 결정 로그 append (SPEC §8). 배정 시 1차, 검증 후 **같은 `id`로 2차**.
2. 실행별 원시 로그 보존.
3. 에러 리포팅에 태그와 모듈 출처.
4. 정상 비즈니스 상태(결과 없음·분류 실패)를 에러로 올리지 않는다. `catch` 후 무동작 금지 — 실패에는 사용자에게 보이는 상태가 있어야 한다.

**완료 판정**: 작업 1건 실행 후 jsonl에 같은 `id`의 줄이 정확히 2개 있다.

## 사람에게 올리는 조건

- 실제 비용이 발생하는 실행을 처음 띄우기 전 (특히 Astra·Fable max 조합, 합산 $10.89)
- 되돌리기 어려운 변경, 외부 쓰기
- 매트릭스 "해당 없음" 분류
- 상한(반복·노드·비용) 도달
- 매트릭스 원본과 구현 테이블 불일치 — **구현을 멈추고 보고한다**
- CLI 실제 플래그가 SPEC §0과 다를 때 — 추측한 플래그로 진행하지 않는다

## 중단 조건

- S1이 안 도는데 S2 이후로 넘어가지 않는다
- 같은 실패를 2회 연속 같은 방식으로 재시도하지 않는다
- 상한 없는 반복 방식은 머지하지 않는다
