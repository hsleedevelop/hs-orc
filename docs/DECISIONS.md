## D-001 — v1은 TUI, v2는 GUI

**배경**
초기 스케치가 "tui or gui"로 열려 있었다.

**결정**
1차 릴리스는 TUI. GUI는 v2로 미룬다.

**근거**
오케스트레이터가 띄우는 대상(`claude`, `codex`, `cursor-cli`)이 전부 터미널 CLI다. 같은 터미널에 사는 편이 배포·통합이 단순하다. GUI가 실질적으로 나은 부분(dashboard, 그래프 시각화)은 코어가 안정된 뒤에 붙여도 늦지 않다.

**영향**
**Core(분류·라우팅·어댑터·진행 방식)는 UI를 모르는 헤드리스 라이브러리여야 한다.** v2에서 Shell만 교체한다. `core/`가 `shell/`을 import하면 lint 에러가 나게 경계를 강제한다. v2에서 Core 수정이 필요하면 v1 설계가 틀린 것이고, 그 경우 GUI를 진행하지 말고 경계를 먼저 고친다.

**상태** 확정

## D-002 — 진행 방식 3종의 의미론

**배경**
`/pingpong`, `/loop`, `/graph` 중 이 환경에 존재하는 것은 `/loop`(Claude Code 내장 스킬)뿐이다. 나머지 둘은 호출하면 되는 기존 기능이 아니라 이 제품이 정의할 대상이었다.

**결정**

| 방식 | 성격 | 자율성 |
|---|---|---|
| `/pingpong` | 대화형 | **비자율** — 사용자가 매 턴 개입 |
| `/loop` | loop-engineering | 자율 반복 |
| `/graph` | graph-engineering | 자율 DAG |

**근거**
세 방식을 같은 축(자율성)으로 갈라야 상한 정책이 일관된다. pingpong은 매 턴 사용자 승인이 있으므로 턴 제한이 불필요하고, loop와 graph는 사람이 안 보는 동안 도니까 상한이 **필수**다.

**영향**
- `/pingpong`: 1턴 = 1작업. 턴 종료 시 결과·다음 제안을 제시하고 사용자 입력을 기다린다. 최대 턴 제한 없음, 누적 비용 상시 표시.
- `/loop`: Goal · Planner · Executor · Evaluator · Critic · Recovery · Stop을 분리된 구성요소로. **최대 반복 수 없이는 구현하지 않는다.**
- `/graph`: 노드별 독립 배정, 실행 전 순환 검출 필수, 병렬은 쓰기 대상 비겹침 확인 시에만, 부분 실패 전파 규칙을 노드마다 선언.
- 세 방식 공통으로 **상한 도달 시 정상 중단을 정상 완료보다 먼저 검증한다.**

**상태** 확정 (단, `/pingpong`의 "대화형"이 사용자와의 대화라는 해석은 확인 대기 — D-006)

## D-003 — `/loop`의 Evaluator에 reviewer 슬롯 모델을 쓴다

**배경**
매트릭스는 모든 행에 independent reviewer를 둔다. 자율 루프에서 이 reviewer가 어디에 들어가는지가 정해지지 않았다.

**결정**
`/loop`의 Evaluator 역할에 매트릭스의 reviewer 슬롯 모델을 배정한다.

**근거**
Evaluator는 "결과가 기준을 충족했는가"를 판정하는 자리다. 이것을 primary와 같은 모델이 하면 자기 채점이 된다. 매트릭스가 요구하는 독립 리뷰가 루프 안에서 실현되는 유일한 자리다.

**영향**
루프 1사이클 비용 = primary 1회 + reviewer 1회. 비용 산정과 상한 계산이 이를 반영해야 한다.

**상태** 확정

## D-004 — `cursor-cli -p`는 전역 대체가 아니라 모델별 대체다

**배경**
초기 스케치는 엔진으로 claude / codex / cursor-cli 셋을 들었으나, 매트릭스 11행 어디에도 Cursor 모델이 없다. Cursor의 역할이 정의되지 않은 상태였다.

**결정**
`cursor-cli -p`를 **대체 하네스**로 둔다 — 매트릭스가 배정한 모델을 다른 하네스로 돌리는 경로다. 단 **모델별로만** 성립한다.

**근거 (실측, 2026-09-20 `cursor-agent --list-models`)**

| 매트릭스 모델 | Cursor 커버 |
|---|---|
| Luna / Terra / Sol | `gpt-5.6-{luna,terra,sol}-{effort}` ✅ |
| Sonnet / Opus / Fable | `claude-{sonnet-5,opus-5-thinking,fable-5-1}-{effort}` ✅ |
| **Astra** | **없음** ❌ |
| **Haiku** | **없음** ❌ |

8모델 중 6개만 커버한다. Astra는 11행 중 6행(primary 4·reviewer 2)에, Haiku는 1행의 reviewer에 등장하므로 전역 대체는 성립하지 않는다.

**영향**
`engines.json`에 모델별 가용성 테이블을 둔다. `supports()`가 이를 읽고, 지원하지 않는 조합에 대체를 시도하면 **명시적 실패**다 — 가장 가까운 모델로 말없이 바꾸지 않는다.

**상태** 확정

## D-005 — 바이너리 이름은 `cursor-cli`, 해석은 폴백으로

**상태** 확정

## D-006 — `/pingpong`의 "대화형" 해석 (확인 대기)

**배경**
"대화형"이 **사용자와의 대화**인지 **primary↔reviewer의 교대**인지 두 가지로 읽힌다.

**현재 해석**
사용자와의 대화 — 사용자가 매 턴 개입하는 human-in-the-loop 진행.

**근거**
다른 두 방식을 "loop-engineering", "graph-engineering"이라는 규율 이름으로 부른 것과 달리 `/pingpong`만 성격("대화형")으로 불렀다. 자율/비자율 축에서 유일한 비자율 방식으로 두면 세 방식이 서로 겹치지 않는다.

**뒤집힐 경우의 영향**
primary↔reviewer 교대라면 **자율 실행**이 되므로 최대 왕복 수, 수렴 판정 기준, 교착 시 중단 조건이 전부 필수가 된다. 상한 정책이 D-002와 달라진다.

**상태** 확인 대기

## D-007 — `/loop`는 자체 구현 (기본안)

**배경**

**결정 (기본안)**

**상태** 기본안 — S4 착수 전 확정 필요

## D-011 — effort 검증은 어댑터에서 **던진다**

**배경**
세 엔진의 effort 표기가 전부 다르다.

**결정**
정규 어휘 `low | medium | high | xhigh | max`를 두고, 어댑터가 CLI에 넘기기 **전에** 검증해 밖의 값이면 예외를 던진다. 조용한 기본값 폴백을 만들지 않는다.

**근거 (실측, 2026-09-20)**
`claude -p --effort bogus` 실행 시 출력: `Warning: Unknown --effort value 'bogus' — ignoring it and using the default effort.` **경고만 내고 기본 effort로 실행된다.** 잘못된 effort로 돌아도 아무도 모르므로 어댑터 사전 검증이 유일한 방어선이다.

**영향**
| 정규값 | claude | codex | cursor |
|---|---|---|---|
| low~max | `--effort <v>` | `-c model_reasoning_effort="<v>"` | 모델 id 접미사 `-<v>` |

codex의 `ultra`는 매트릭스에 없으므로 정규 어휘에 넣지 않는다. 매트릭스의 `Mid`는 `medium`으로 매핑한다.

**상태** 확정

## D-015 — `/pingpong`의 "대화형"은 사용자와의 대화다 (Q1 확정)

**배경**
D-006이 두 해석을 열어 두었다. ① 사용자와의 대화(human-in-the-loop) ② primary↔reviewer 자율 교대.

**결정**
①이다. 매 턴 **사용자 입력을 기다린다.** 따라서 최대 턴 수 제한을 두지 않는다 — 상한의 역할을 사용자 승인이 대신한다. primary와 reviewer를 같은 턴 안에서 교대로 붙일 수는 있으나, 그 교대를 **자동으로 반복하지 않는다.**

**근거**
②로 가면 pingpong이 사실상 두 번째 loop가 되고, 최대 왕복 수·수렴 판정·교착 중단이 전부 필수가 되어 D-002(자율성으로 방식을 가른다)가 무너진다. 사용자 결정(2026-09-20).

**영향**
`/pingpong`만 비자율이므로 턴 상한 대신 **누적 비용 상한**만 공유한다. 상한 도달 시 다음 턴을 시작하지 않고 사람에게 올린다.

**상태** 확정 — Q1 종결

## D-017 — 누적 비용 상한 기본값은 $20 (Q3 확정)

**배경**
자율 방식(`/loop`, `/graph`)은 무한 반복이 곧 비용이다. 상한이 없으면 사고가 난다.

**결정**
누적 비용 상한 기본값 **$20**. `data/limits.json`에 두고 사용자가 덮어쓸 수 있다.

**근거**
매트릭스 최고 조합(Fable+Astra $10.89)으로 **2사이클을 돌면 상한에 닿는다.** 사고가 나도 한 자릿수 사이클에서 멈추고, 정상 작업이 상한에 걸리면 그것 자체가 "이 작업은 방식이 틀렸다"는 신호가 된다. 사용자 결정(2026-09-20).

**영향**

## D-019 — Ink을 쓰되 JSX는 쓰지 않는다

**배경**
Node 25의 타입 스트리핑은 **JSX를 처리하지 못한다.** JSX를 쓰려면 빌드 단계(esbuild/tsc emit)를 추가해야 하고, 그러면 테스트 실행 방식(`node --test` 로 `.ts` 직접 실행)까지 바뀐다.

**결정**
화면은 `createElement`(`el` 헬퍼)로 작성하고 **빌드 단계를 추가하지 않는다.** 대신 화면 로직을 **뷰모델(순수 `.ts`)로 분리**하고 Ink 렌더 층은 얇게 유지한다.

**근거**
렌더 층이 얇으면 JSX의 이득이 작고, 빌드 단계는 S0에서 세운 게이트(타입 스트리핑 기반 `node --test`)를 통째로 바꾼다. 뷰모델 분리는 Core가 UI를 모른다는 원칙(D-001)과도 같은 방향이고, 테스트가 터미널을 띄우지 않아도 된다.

**영향**
화면이 커져 `createElement` 중첩이 읽기 어려워지면 그때 esbuild를 도입한다 — **그 전까지는 렌더 층이 얇지 않다는 신호로 읽는다.**

**개정 2026-09-21 (S7)** — 탈출구를 **렌더러에만** 열었다. Electron 렌더러는 Chromium이라 TS도 bare specifier도 못 읽어 번들러 없이는 React가 아예 안 뜬다(선택이 아니라 제약). 그래서 `esbuild`로 `src/shell/gui/renderer/` 하나만 묶고, 메인 프로세스와 TUI는 타입 스트리핑 그대로 둔다. **번들러가 생겼어도 JSX는 여전히 안 쓴다** — 두 셸의 화면 코드가 같은 모양이어야 v1↔v2 이식을 눈으로 대조할 수 있다. 렌더러는 DOM lib이 필요해 `tsconfig.renderer.json`으로 갈라 타입 검사한다(게이트는 두 tsc를 모두 돌린다).

**상태** 확정

## D-024 — 진입점은 `.mjs` 래퍼 하나이고 빌드 산출물을 만들지 않는다

**배경**
v1~v2 내내 실행 경로가 `npm run` 뿐이었다 — 이 저장소 안에서만 돈다. 라우터는 **작업 중인 다른 프로젝트**에서 불려야 쓸모가 있다.

**결정**
`bin/hs-orc.mjs` 하나를 `package.json` 의 `bin` 으로 노출하고, 이 파일이 `src/shell/` 의 `.ts` 를 **그대로** 띄운다. `dist/` 를 만들지 않는다(D-019). 래퍼 자신만 `.mjs` 다 — 진입점은 타입 스트리핑 없이 떠야 하기 때문이다.

- `hs-orc "<작업>"` → `src/shell/cli.ts` · `hs-orc tui` → `tui/main.ts` · `hs-orc gui` → 렌더러 번들 → `electron gui/main.ts`
- cli·tui 는 **하위 프로세스를 더 띄우지 않는다.** `process.argv` 만 실제 호출 모양으로 바꾸고 `import()` 한다 — 래퍼가 한 겹 끼면 TUI 의 raw mode 와 엔진 프로세스 그룹 종료(SPEC §3)가 그만큼 멀어진다.
- `npm run tui|gui|build:gui` 도 이 래퍼를 부른다. 실행 경로를 둘로 두지 않는다.

**경로 해석은 두 기준으로 갈리고, 그게 의도다**

| 대상 | 기준 | 이유 |
|---|---|---|
| `data/{matrix,engines,limits,verify}.json` | **설치 위치** (`import.meta.dirname`) | 어디서 부르든 같은 매트릭스여야 한다 |
| `.hs-orc/runs`, `.hs-orc/unclassified.jsonl` | **cwd** | 실행 산출물은 작업 중인 프로젝트에 쌓여야 한다 |
| 결정 로그 | `~/.claude/logs/` (`HS_ORC_DECISION_LOG` 로 분리) | 프로젝트를 가로지르는 기록이다 |

한쪽이 뒤집히면 "다른 디렉터리에서 쓸 수 있다"가 조용히 거짓이 되므로 `src/shell/__tests__/bin.test.ts` 가 프로세스 수준에서 고정한다.

**타입 스트리핑은 capability 로 판정한다.** `process.features.typescript` 를 보고 꺼져 있으면 즉시 던진다. Node 버전 표를 코드에 적지 않는다 — 표는 낡고, 낡은 표는 조용한 오진이 된다.

**상태** 확정 — 2026-09-21 실측

## D-025 — 쓰기 권한은 primary 슬롯만, 그것도 명시적 옵트인

**배경**
진입점 실사용에서 **primary(codex)가 read-only 샌드박스로 떠서 파일을 못 고쳤다.** "수정안"만 내고 끝났고 reviewer 가 그것을 FAIL 로 잡았다. 두 슬롯 설계는 작동했지만, 라우터가 광고하는 "실행"이 실제로는 안 되고 있었다.

**결정**

1. **`engines.json` 에 엔진별 쓰기 인자를 선언한다.** 실측 `--help` 기준이고, 워크스페이스 밖까지 여는 값은 선언하지 않는다.

   | 엔진 | 쓴다 | 쓰지 않는다 |
   |---|---|---|
   | codex | `-s workspace-write` | `danger-full-access` |
   | claude | `--permission-mode acceptEdits` | `bypassPermissions` (쉘까지 열린다) |
   | cursor | `--force` | `--yolo` (같은 것의 별칭) |

2. **reviewer 는 절대 받지 않는다.** `ResolvedSlot` 에 `role` 을 두고 `core/executor.ts` 한 곳에서 `options.write === true && slot.role === 'primary'` 로만 부여한다. 호출자가 무엇을 넘겨도 reviewer 는 읽기 전용이다. 판정 대상을 스스로 고칠 수 있는 검증자는 독립 검증자가 아니다 (D-003·INV-1).

3. **기본은 꺼짐, `--write` 로 옵트인.** PLAN "사람에게 올리는 조건"에 **외부 쓰기**가 있다. `--run` 이 비용 승인이라면 `--write` 는 쓰기 승인이고, 둘은 다른 결정이다. 쓰기 여부는 **승인 전 화면에 비용과 나란히** 찍는다.

4. **선언이 없는 엔진에 쓰기를 요청하면 던진다.** 읽기 전용으로 조용히 떨어뜨리면 아무것도 안 바꾼 산출물이 "고쳤다"로 통과한다 — hs-00-core 가 금지하는 조용한 폴백이다.

**기각**
- *기본을 켜짐으로* — `--run` 하나로 비용과 파일 수정을 동시에 승인하게 된다. 되돌리기 어려운 쪽을 끼워 파는 셈이다.
- *`bypassPermissions` / `danger-full-access`* — 워크스페이스 밖 쓰기와 임의 쉘이 열린다. 얻는 것(프롬프트 0회)에 비해 잃는 것이 크다.
- *reviewer 에게도 쓰기* — "reviewer 가 직접 고치면 빠르다"는 유혹이 있으나, 그 순간 산출물과 판정의 출처가 같아져 D-009 의 두 슬롯이 무의미해진다.

**실측 (2026-09-21, `/tmp` 빈 git repo)**
`hs-orc "broken.ts 의 타입 에러를 고쳐라" --write --run` → Luna(codex)가 **파일을 실제로 수정**(`git diff` 1 file changed, `number` → `string`), Haiku(reviewer)는 `tsc 실행 권한 미획득`을 사유로 들며 `FAIL` — reviewer 가 읽기 전용으로 남았다는 실증이다. `--write` 없이는 종전대로 수정안만 낸다.

## D-026 — LLM 분류 폴백은 기본으로 돈다, 대신 돌았다고 말한다 (Q8 확정)

**배경**
규칙 표(`core/classify.ts`)는 행별 키워드 몇 개에 의존한다. 실사용 첫 작업 "…켤 수 있게 하라" 가 R03 키워드(`구현해`·`만들어`)에 안 걸려 **그냥 실패했다**(PLAN S9-2). 명령형 어미 하나 차이로 제품이 멈춘다.

**결정**
`--classify-llm` 을 **기본 켜짐**으로 바꾸고 `--no-classify-llm` 으로 끈다. 폴백이 돌면 **반드시 한 줄을 찍는다**: `분류 규칙 무매치 → Haiku·low 로 분류만 재시도 (+$0.001 내외 · --no-classify-llm 으로 끈다)`.

- **말없이 도는 유료 호출은 없다.** 기본을 켜는 대가로 비용 표기를 의무화한다 — SPEC §7 "실행 전 비용 표시" 를 분류 단계까지 넓힌 것이다.
- **폴백 실패는 삼키지 않는다.** 바이너리가 없거나 호출이 실패하면 `[notice][pipeline/classify-fallback]` 을 찍고 미분류 경로로 내려간다. 폴백이 죽어도 전체가 죽지는 않되 침묵하지도 않는다.
- 옛 `--classify-llm` 플래그는 **계속 받는다**(이제 무해한 명시). 지우면 기존 스크립트에서 그 낱말이 **작업 문자열로 섞여 들어간다.**
- 곁다리로 같은 구멍을 막았다: **모르는 `--옵션` 은 던진다.** 전에는 `--오타` 가 조용히 작업 문자열의 일부가 됐다.

**기각**
- *키워드 표를 넓힌다* — 어미·표현이 무한해 두더지잡기다. 표가 커질수록 왜 그 행으로 갔는지 설명하기도 어려워진다.
- *현상 유지(기본 꺼짐)* — "돈 나가는 호출은 전부 옵트인" 원칙은 맞지만, 분류 1회는 $0.001 규모이고 그 대가가 **평범한 문장에서의 실패**다. 비용 표기로 원칙의 실질(사용자가 알고 쓴다)을 지킨다.

**세 셸이 같은 함수를 쓴다** — `core/pipeline.ts` 의 `routeWithFallback`. 처음에는 CLI 안에 인라인으로 뒀는데, 그러면 셸마다 복제되거나(세 벌) 한쪽에만 있어 **같은 입력이 다르게 동작한다.** 그래서 폴백을 Core 로 올리고 인라인을 지웠다. 셸은 `fallback.line` 을 자기 방식으로 그릴 뿐이다(CLI 는 stderr, TUI·GUI 는 뷰모델 `notes`).

이 때문에 TUI 의 `RunScreen` 과 GUI 의 `plan()` 이 **비동기**가 됐다. 렌더 중 동기 라우팅은 더 이상 못 한다 — 그 대가로 셸 간 동작 차이가 없다.

**분류는 결정적이지 않다.** 같은 문장이 S9 에서는 R01, D-026 실측에서는 R03 으로 갔다. 폴백은 "무엇이든 고른다" 가 아니라 "고른 근거를 표기한다"(`Haiku·low 분류 R03`)로 정직해진다.

## D-027 — 단가는 선언으로 받고, 근거 등급을 하나 더 만든다

**배경**
`claude` 만 `total_cost_usd` 를 돌려준다. codex·cursor 는 **토큰만** 주므로 단가표가 없으면 AA 벤치마크 추정치로 누적된다. 그런데 토큰은 이미 파싱돼 있다 — 단가만 있으면 훨씬 정확해진다.

**결정**

1. **`data/pricing.json` 에 모델 id 별 단가를 선언한다.** `verify.json` 과 같은 방식이다 — **제품은 단가를 추측하지 않는다.** 저장소 기본값은 **비어 있다.**
2. **출처를 셋으로 나눈다.** 우선순위는 `actual` > `metered` > `estimate` 다.

   | 출처 | 뜻 |
   |---|---|
   | `actual` | 엔진이 돌려준 값 (`total_cost_usd`) |
   | `metered` | 엔진이 보고한 **측정 토큰** × **선언 단가** |
   | `estimate` | 매트릭스의 AA 벤치마크 작업당 비용 |

   `metered` 를 `actual` 이라 부르지 않는다 — **벤더가 청구한 금액이 아니다.** 측정치와 선언값의 곱이고, 단가가 틀리면 결과도 틀린다. 이름이 그 차이를 지고 있어야 한다.
3. **섞이면 무엇이 섞였는지 누적 표시에 적는다**: `$1.2340 / $20 (실측+토큰×선언단가)`.
4. **선언이 없는 모델은 `undefined` 다. 0 이 아니다.** 0 으로 떨어뜨리면 "공짜로 돌았다" 가 되어 누적 비용과 상한이 통째로 거짓이 된다.

**기각**
- *단가를 코드에 박는다* — 모델·가격은 바뀌고, 틀린 단가로 계산한 "실비" 는 추정치보다 나쁘다(정확해 보이기 때문이다).
- *`metered` 를 `actual` 로 합친다* — 두 값의 신뢰도가 다르다. SPEC §2.5 가 근거 등급을 섞지 말라고 한 것과 같은 이유다.
- *단가가 없으면 추정치로 조용히 대체* — 이미 그렇게 한다. 다만 **어느 쪽인지 표시**하는 것이 이 결정의 핵심이다.

**상태** 확정 — 2026-09-21. 단가표 자체는 비어 있다: 실제 값은 쓰는 사람이 자기 요금제로 채운다.

## D-028 — 워크트리는 저장소 안이 아니라 홈에 둔다

**배경**
`--write`(D-025)를 켜면 primary 슬롯이 파일을 고친다. 그 대상이 **지금 사람이 편집 중인 작업 트리**면 되돌리기가 사람 몫이 된다. GUI 에 git worktree 를 붙이기로 하면서 "어디에 만들 것인가" 가 갈렸다.

**결정**

1. **위치는 `~/.hs-orc/worktrees/<저장소>/<이름>` 이다.** 저장소 밖이다. `HS_ORC_WORKTREES` 로 뿌리를 옮길 수 있다.
2. **저장소 폴더 이름에 실제 경로 sha256 앞 8자를 붙인다** (`hs-orc-ba831a89`). 이름만 쓰면 서로 다른 저장소의 `api` 두 개가 같은 자리를 노린다.
3. 브랜치는 `hs-orc/<이름>` 이고, **만들면 그 안으로 바로 들어간다.** 만들고 본체에 남으면 쓰기를 가둔 뜻이 없다.
4. 삭제는 `--force` 를 쓰지 않는다. 커밋 안 한 변경이 있으면 git 이 거절하고 그 말을 그대로 올린다. 브랜치는 `git branch -d`(머지된 것만)로만 지우고, 거절당하면 **남기고 그렇다고 말한다.**
5. **새 워크트리에는 의존성이 따라오지 않는다 — 실행 전에 알린다.** `node_modules` 가 없으면 검증 명령도, primary 가 스스로 돌리는 test 도 성립하지 않는다. 첫 실사용에서 primary 가 실제로 여기서 막혔다(그것도 **돈을 쓴 뒤에**). 세 셸이 같은 감지기(`shell/deps.ts`)를 쓰고, **설치를 대신 해 주지는 않는다** — 네트워크와 시간이 드는 일이라 사람이 결정한다(D-022 의 "제안만 한다" 와 같은 정신). lock 파일이 있으면 `npm ci` 를 제안한다: 워크트리의 의존성 버전이 본체와 갈리면 검증이 거짓이 된다.
6. **실행 기록이 남아 있으면 삭제를 거절한다.** 산출물은 cwd 기준으로 쌓이므로(`bin/hs-orc.mjs`) 워크트리를 지우면 그 안의 `.hs-orc/runs/` 도 같이 사라진다. "증거로 종료" 하는 제품이 증거를 조용히 버리면 안 된다 — **2026-09-22 에 첫 실사용의 원시 로그를 실제로 이렇게 잃었다**(브랜치를 지우는 도구가 워크트리까지 함께 제거했다). git 이 dirty 를 거절하는 것과 같은 자리에서 같은 방식으로 막는다.

**근거**
저장소 안(`<repo>/.hs-orc/worktrees/`)에 두면 세 가지가 따라온다: 프로젝트마다 무시 설정을 강요하고, 검색·빌드·감시 도구가 저장소를 재귀로 훑고, 워크트리 안에 워크트리가 중첩된다. **ao 도 같은 이유로 홈(`~/.ao/data/worktrees/<repo>/`)에 둔다** — 같은 문제를 먼저 겪은 도구의 선택이다.

이것은 `bin/hs-orc.mjs` 가 못 박은 두 기준에 **세 번째를 더한다.**

| 기준 | 무엇 |
|---|---|
| 설치 위치 | `data/*.json` — 어디서 부르든 같은 매트릭스다 |
| cwd | `.hs-orc/runs`, `.hs-orc/unclassified.jsonl` — 산출물은 작업 중인 프로젝트에 쌓인다 |
| **홈** | **워크트리, 최근 프로젝트 목록 — 프로젝트를 건너다니는 사용자의 상태다** |

**기각**
- *저장소 안 `.hs-orc/worktrees/`* — 위 세 가지. 첫 구현이 여기였고, 실제로 저장소가 지저분해졌다.
  가상의 우려가 아니다: **이 저장소 자신이 그렇게 돼 있었다.** 다른 에이전트 도구가 `.claude/worktrees/` 에 워크트리 두 개를 만들어 뒀고, 무시 설정이 없어 415MB 가 `git add .` 한 번 거리에 놓여 있었다(2026-09-22 `.gitignore` 에 추가).
- *형제 폴더 `../<repo>-<이름>`* — 부모 디렉터리에 쓰는 것은 권한도 관례도 불확실하다. iCloud 동기화 폴더 안이면 더 나쁘다.
- *`git worktree remove --force`* — 편하지만 커밋 안 한 남의 작업을 말없이 버린다. 거절하고 사유를 보여주는 편이 낫다.

**영향**
`.hs-orc/` 라는 이름이 **두 자리에 있다** — cwd 아래(실행 산출물)와 홈 아래(워크트리·최근 목록). 같은 이름이 다른 뜻으로 쓰이므로 헷갈릴 수 있어 여기 적어 둔다. 판별 기준은 "이 데이터가 프로젝트의 것인가, 사람의 것인가" 다.

**상태** 확정 — 2026-09-21. GUI 실측으로 생성→삭제 왕복 확인(워크트리·브랜치·홈 폴더·최근 목록 정리, 같은 저장소의 다른 도구 워크트리 무영향).

## D-029 — 작업 폴더 전환은 GUI 에만 둔다

**배경**
GUI 를 `process.cwd()` 에서 떼어내면서, CLI·TUI 에도 같은 전환을 줄지가 남았다.

**결정**
**전환은 GUI 만 한다.** CLI·TUI 는 `process.cwd()` 고정이고, `--cwd` 같은 옵션을 만들지 않는다.

**근거**
**셸이 이미 폴더를 고르는 도구다.** CLI 에 `--cwd` 를 더하면 폴더의 진실이 둘이 되고(`cd` 한 자리 vs 플래그), 어느 쪽이 이겼는지 매번 설명해야 한다. TUI 도 같은 터미널에 산다.

**GUI 만 셸이 없다.** 아이콘으로 띄우면 cwd 가 무엇인지 사용자가 알 길이 없고, 그 상태로 `--write` 를 켜는 것이 이 제품에서 가장 위험한 조작이다. 전환 UI 는 그 공백을 메우는 것이지 편의 기능이 아니다. 화면에 폴더가 **항상 보이는** 것이 전환 기능 자체보다 중요하다.

**기각**
- *세 셸 전부에 `--cwd`* — 위. 그리고 CLI 에서 그 플래그를 쓸 이유가 `cd` 말고 없다.
- *Core 에 전역 작업 폴더를 둔다* — Core 가 UI 상태를 갖게 된다. D-001 이 막은 방향이다.

**영향**
`GuiService.workdir` 가 작업 폴더의 **유일한 소유자**다. 이 클래스 안에서 `process.cwd()` 를 다시 읽는 곳이 생기면 화면의 폴더와 실행 폴더가 갈린다 — 가장 위험한 종류의 버그라 테스트로 고정했다.

분류기(`core/classify-llm.ts`)도 같은 폴더에서 돈다. 처음에는 여기만 `process.cwd()` 로 남아 있었다(Q9) — 읽기 전용이라 오동작은 아니지만 **화면이 말하는 폴더와 실제로 띄운 폴더가 갈린다.** `cwd` 를 `routeWithFallback` 의 옵션으로 올려 GUI 만 넘긴다. 기본값이 `process.cwd()` 라 CLI·TUI 는 그대로다.

**이것은 D-001 위반이 아니다.** Core 가 UI 를 아는 것이 아니라, **숨어 있던 전역 의존(`process.cwd()`)을 인자로 드러낸 것**이다. 방향이 반대다 — Core 는 더 순수해졌다.

**상태** 확정 — 2026-09-21. Q9 는 2026-09-22 에 닫았다.

## D-030 — 요금제는 선언으로 받고, 상한은 청구되는 것에만 건다

**배경**
D-027 이 근거 등급을 셋으로 나눴다: `actual`(엔진이 돌려준 값) > `metered`(측정 토큰 × 선언 단가) > `estimate`(AA 벤치마크). 이 순서의 근거는 **"벤더가 청구한 금액에 얼마나 가까운가"** 였다.

그 전제가 틀렸다. 이 저장소를 쓰는 사람은 claude·codex·cursor 를 **전부 구독제**로 쓴다. 구독제에서는 claude 가 주는 `total_cost_usd` 조차 청구되지 않는다 — API 로 썼다면 들었을 환산액이다. 세 등급이 전부 같은 배를 타고 있었고, **D-017 의 누적 상한 $20 은 아무것도 막지 않고 있었다.**

**결정**

1. **요금제는 엔진별 선언이다** (`engines.json` 의 `plan: "subscription" | "api"`). 제품이 알아낼 수 없다 — 같은 CLI 를 구독제로도 API 키로도 쓴다. 타입에서 **필수**다: 빠지면 금액 표시가 청구인지 환산인지 말할 수 없다.
2. **슬롯이 자기 요금제를 들고 다닌다** (`ResolvedSlot.plan`). 그래야 `Budget` 이 카탈로그를 몰라도 된다.
3. **금액 상한은 `billedUsd`(api 요금제 charge 합)에만 건다.** 구독제 환산액은 `convertedUsd` 로 따로 센다. 둘을 합친 `spentUsd` 는 **표시용이고 상한 판정에 쓰지 않는다.**
4. **구독제에서 막는 것은 토큰이다** (`limits.json` 의 `tokenBudget`, 기본 200만). 실제로 희소한 자원은 돈이 아니라 사용량 한도(주간·5시간 rate limit)이고, 그에 비례하는 것이 토큰이다.
5. **두 상한 중 하나라도 닿으면 멈춘다** — `Budget.limitReached()`. 실행을 멈출지 묻는 곳은 전부 이것을 쓴다. `exceeded()`(금액)만 보면 구독제에서 아무것도 막지 못한다.
6. **토큰을 보고하지 않은 사이클은 0 으로 채우지 않는다.** 따로 세어(`unreportedCycles`) 누적 표시에 드러낸다 — 0 으로 떨어뜨리면 "공짜로 돌았다" 가 되어 상한이 통째로 거짓이 된다 (D-027 의 `undefined` 규칙과 같은 이유).
7. **표시가 거짓말하지 않는다.** 전부 구독제면 `$0.2730 API 환산 · 구독제라 청구되지 않는다 · 토큰 12345/2000000` 이다. `/ $20` 을 붙이면 그 상한이 이 숫자를 막는다는 거짓말이 된다.

**기각**
- *상한을 아예 끈다* — D-017 이 "자율 방식은 무한 반복이 곧 비용" 이라 적은 근거를 포기하는 선택이다. 구독제에서도 무한 반복은 한도를 태운다.
- *사이클 수로 센다* — 구현은 가장 쉽지만 R01 한 번과 R11 한 번을 같게 세어 실제 소모와 많이 어긋난다.
- *전역 요금제 선언 하나* — 엔진마다 요금제가 다를 수 있다(한쪽만 API). 거짓이 되는 순간이 온다.
- *`metered` 를 아예 끈다* — 청구되지 않아도 **배정 간 상대 비교**에는 그대로 쓸모 있다. 첫 실사용에서 R03 $7.08 vs R01 $0.39 라는 18배 차이를 보고 배정을 내린 그 판단이 그것이다.

**영향**
**1단계(표시만 고치기)와 2단계(토큰 상한)를 나눌 수 없었다.** 금액 상한을 청구분에만 거는 순간 구독제 사용자에게 상한이 사라지고, 그것은 `limits.json` 의 "상한이 없는 방식은 머지하지 않는다"(PLAN S4) 위반이다. 실제로 1단계만 넣었을 때 상한 테스트 3건이 곧바로 빨간불이 됐다 — 쪼개려던 계획을 그 실패가 막았다.

`SlotRun` 에 `usage` 가 생겼다. `rawStdout`(SPEC §3.7)에 이어 두 번째 경계 확장이고, 이유도 같다: **어댑터가 이미 알고 있는 것을 셸까지 내려보내지 않으면 상한도 단가도 거짓이 된다.**

**상태** 확정 — 2026-09-22. 음성 대조: `limitReached()` 를 `exceeded()` 로 되돌리면 토큰 상한 테스트 3건이 전부 실패하고, 원복하면 통과한다.

## D-031 — 제품 단위를 "작업 1건"에서 "대화 세션"으로 올린다 (지휘자 층)

**배경**
첫 GUI 실사용(2026-09-23)에서 "넌 누구니" 를 전송하자 **아무 일도 일어나지 않았다.** 분류 실패 → 승인 버튼 없음 → 끝. 원인은 화면이 아니라 제품 정의에 있었다.

- PRD §2 는 제품을 **작업 1건 라우터**로 정의했다. 채팅·세션·결과 처리가 요구사항 어디에도 없다.
- §1 하한선의 "직접 처리" 는 원래 Claude Code 세션 안에서 delegation-router 를 쓸 때 **"메인 세션인 내가 한다"** 는 뜻이다. 이 제품은 라우터만 옮겨 오고 **그 "나" 를 옮겨 오지 않았다** — 그래서 `direct` 는 "엔진을 띄우지 않는다" 로 끝나고 아무도 답하지 않는다.
- 유일한 대화형인 `/pingpong` 은 CLI 에만 있고, **세션 시작 때 배정 1회로 고정**되며, 매 턴이 새 비대화 실행이라 **맥락이 이어지지 않는다** (`core/modes/pingpong.ts` — `execute(slot, prompt)` 뿐, 어댑터에 resume 경로 없음).

사용자가 원한 것은 **프로젝트(또는 스크래치)로 들어가 orc 채팅창에 요청하면, orc 가 모델·effort 를 정해 위임하고 결과를 받아 처리하는** 제품이다. 진입·세션 모양은 AO(`Untrivial-ai/agent-orchestrator`)를 참조한다.

**결정**

1. **진입 단위는 세션이다.** 세션은 둘 중 하나로 시작한다.
   - `project` — 폴더 기준. D-029 의 폴더·워크트리 전환을 그대로 쓴다.
   - `scratch` — 폴더 없이 시작하는 단일 세션. 엔진이 cwd 를 요구하므로 `~/.hs-orc/scratch/<id>/` 를 만든다. git 이 아니고 **쓰기는 기본 꺼짐**이다.
2. **세션의 진실은 orc 가 가진 대화 기록이다.** append-only (`<세션 폴더>/.hs-orc/sessions/<id>.jsonl`). 엔진 세션 파일이 아니다.
3. **지휘자는 하이브리드다.** 메시지 1건마다:
   - **라우팅은 지금처럼 결정론 코드**다 — 분류 → 하한선 → 매트릭스 배정. G1(매번 같은 기준)을 모델 판단에 넘기지 않는다.
   - **직접 답** — 하한선에 걸렸거나 분류가 안 되는 메시지(잡담·질문·설명 요청)는 **저비용 모델**(분류 폴백과 같은 계층)이 대화 맥락으로 답한다. 작업처럼 보이면 답 안에서 **"업무 행 Rxx 로 위임할까"를 제안**만 한다 — 임의 배정은 여전히 만들지 않는다 (FR-1).
   - **위임** — 기존 Core 그대로: 배정·비용 → **승인** → 두 슬롯 → 증거.
   - **결과 처리** — primary 출력·reviewer 판정·증거를 대화 기록에 붙이고, 지휘자가 요약과 **다음 제안**(사다리 상향 포함)을 낸다. **다음 위임을 스스로 시작하지 않는다** (D-015 의 비자율 유지).
4. **맥락 전달은 orc 가 한다.** 위임 프롬프트에 세션 요약 + 최근 턴을 싣는다. 엔진 resume(`claude -p --resume`, `codex exec resume`, `cursor-agent -p --resume`)은 **같은 슬롯(같은 엔진·모델)으로 이어지는 후속**에만 최적화로 쓴다. 턴마다 벤더가 바뀌는 제품에서 resume 을 맥락의 진실로 삼으면 교차 벤더 순간 대화가 끊긴다.
5. **승인 게이트는 위임에만 둔다** (G2). 직접 답은 승인 없이 흐르되 비용 한 줄을 찍고 D-030 의 누적 상한을 공유한다 — 말없이 도는 유료 호출은 없다 (D-026).
6. **`/pingpong` 이 GUI 의 기본 진행이 되고, 배정은 턴마다 다시 한다** (D-015 개정 — 세션 고정 배정을 버린다). `/loop`·`/graph` 는 위임 방식의 하나로 채팅에서 고른다.
7. 불변식은 그대로다: 교차 벤더(위임), 증거로 닫기, 결정 로그 2회(**위임에만** — 직접 답은 SPEC §8 의 "하한선에 걸린 결정은 기록 대상이 아니다" 와 같은 자리다).
8. **Core 에 헤드리스 `ConversationSession` 을 둔다** (D-001). 첫 셸은 GUI, CLI·TUI 는 뒤따른다.

**기각**
- *LLM 에이전트가 지휘자* (claude 세션이 orc 를 도구로 부른다) — 가장 유연하지만 G1 이 모델 판단 안에 숨고, 메시지마다 상위 모델 비용이 든다. 라우팅 근거를 결정 로그에 남길 수 없게 된다.
- *엔진 resume 을 맥락의 진실로* — 위 4. 그리고 세션 파일은 엔진 소유라 D-020 처럼 비공식 경로가 된다.
- *폼을 유지하고 직접 답만 붙인다* — 첫 메시지는 살지만 **결과 처리·후속 요청**이 없다. 사용자가 요구한 절반이 빠진다.

## D-032 — 토큰 상한은 세션 단위로, 지휘자는 사용자 전역 설정에서 떼어 낸다 (+ codex 캐시 이중 계산 수정)

**배경**
v2.1 실사용(PLAN S10, 2026-09-23)에서 앱 누적 토큰 상한 200만(D-030)이 codex 위임 약 2.5회에 닿았다. 내역을 원시 로그로 쪼개니 원인이 둘이었다.

1. **계측 결함.** `Budget.countTokens` 와 `meteredUsd` 가 `inputTokens + cachedInputTokens` 를 더한다. claude 는 두 값이 따로지만 **codex 의 `input_tokens` 는 캐시를 이미 포함한다** — codex 자신의 세션 기록에서 `total_tokens = input_tokens + output_tokens` 가 정확히 성립한다 (`~/.codex/sessions/…jsonl` 의 `token_count`: 227,815,246 + 164,822 = 227,980,068). 그래서 codex 캐시분 약 81만이 두 번 세어졌다 (203만 중). 금액 환산(metered)도 같은 식이라 부풀어 있었다.
2. **Q13.** 위임된 엔진이 사용자 전역 hook·skills·MCP·CLAUDE.md 를 싣고 뜬다. 지휘자(Haiku)가 사용자를 "전하" 라 부른 것이 그 증거다.

**결정**

1. **(결함 수정)** 어댑터가 codex 사용량을 정규화한다: `inputTokens = input_tokens − cached_input_tokens`. 이후 `Usage` 의 의미는 벤더와 무관하게 "캐시 아닌 입력 / 캐시 읽기 / 캐시 쓰기 / 출력" 이 서로 겹치지 않는 네 칸이다.
2. **(A2) 토큰 상한은 세션 단위다.** `ConversationSession` 마다 자기 `Budget` 을 갖는다 (기본 `tokenBudget` 200만 그대로). 앱 누적은 표시만 하고 막지 않는다. D-017 의 "사고는 한 자릿수 사이클에서 멈춘다" 가 세션마다 성립한다. CLI·TUI 의 기존 방식(실행 1회 = Budget 1개)은 그대로다.
3. **(B1) 지휘자만 격리한다.** 직접 답·요약·분류 폴백(Haiku, claude)은 `--setting-sources project,local --strict-mcp-config --disable-slash-commands` 로 띄운다 — 사용자 hook·설정·MCP·skills 를 싣지 않는다. primary·reviewer 는 **격리하지 않는다**: 사용자의 작업 규칙이 위임 품질의 일부다.

**실측** (2026-09-23, 빈 스크래치 폴더, 같은 직접 답 프롬프트 · Haiku·low · 표본 1회씩 — 금액은 캐시 상태에 따라 흔들린다)

## D-033 — 대화 세션에서는 분류 폴백 대신 지휘자가 행을 제안한다 (C4)

**배경**
v2.1 실사용(PLAN S10)에서 대화성 후속 "방금 위임 결과를 한 줄로 다시 설명해" 가 LLM 분류 폴백(직전 요약 hint 포함)에 의해 R02 로 배정됐다. 분류 프롬프트는 "가장 맞는 행" 을 요구하고 hint 가 끌어당긴다. 그런데 세션의 직접 답 경로는 이미 **대화 맥락 전체**를 보고 `SUGGEST: Rxx` 로 행을 제안한다 — 두 경로의 역할이 겹치고, 규칙이 빗나간 메시지는 Haiku 를 두 번 부른다(분류 + 직접 답, 잡담 1회 24초).

**결정**
**대화 세션에서는 규칙 분류가 빗나가면 LLM 분류 폴백을 돌리지 않는다.** 지휘자 직접 답이 대화 맥락으로 답하고, 작업으로 보이면 `SUGGEST` 로 행을 제안한다 — 배정은 사용자가 그 제안을 눌러야 생긴다 (SPEC §6.4.2 의 기존 경로). 규칙 분류(결정론)는 그대로 먼저 돈다.
CLI·TUI 는 대화 맥락이 없으므로 D-026 폴백(기본 켜짐)을 그대로 둔다. 분류 폴백의 hint(D-031 Task 4)는 세션이 유일한 사용처였으므로 걷어낸다.

**실측** (2026-09-23, S10 과 같은 직전 요약 맥락, 격리된 Haiku·low, 표본 8개 × 1회)

| | 대화성 4개 → 위임으로 간 수 | 규칙이 놓친 작업성 1개 |
|---|---|---|
| 현행 (hint 폴백) | 1 ("왜 reviewer 가 FAIL 을 줬어?" → R05) | R01 배정 ("방금 찾은 문제 고쳐줘" — 직전 결과엔 문제가 없었다) |
| C4 (지휘자 SUGGEST) | **0** — 넷 다 맥락을 짚은 답 | NONE — "타입 에러가 없다고 보고됐다" 며 되물음 |

작업성 나머지 3개("테스트도 짜줘"·"리팩터링"·"성능 측정")는 규칙이 R06·R04·R07 로 먼저 잡아 두 경로와 무관하다. S10 에서 오분류됐던 문장은 이번 폴백에서 NONE 이었다 — **폴백 결과가 실행마다 흔들린다.** 표본이 작아 오분류율은 확정하지 않는다; 방향 확인이다. C4 1회 평균 약 $0.013 (격리).

**근거**
- G1 은 넓어지지 않는다: 규칙이 빗나간 뒤의 행 선택은 원래도 모델(폴백)이 했다. 바뀌는 것은 **맥락을 가진 모델이 제안만 한다**는 점이다.
- 오분류 위임이 구조적으로 사라진다 — 승인 게이트 앞의 배정 카드가 잘못 뜨는 일이 없다.
- 호출 2 → 1 (시간·비용).

**기각**

## D-034 — 분류 폴백 비용을 그 실행의 예산에 과금한다 (F2)

**배경**
`classifyWithModel` 이 엔진 결과(`costUsd`·`usage`)를 버리고 행 id 만 돌려준다 — 어떤 셸도 분류 폴백의 비용을 셀 수 없다. 누적 상한(D-017·D-030)이 그만큼 거짓이다. 표시 문구 "+$0.001 내외" 도 틀렸다: 지휘자급 Haiku 호출은 격리(D-032) 상태에서도 1회 $0.013~0.018 로 실측됐다 (분류기 자체는 같은 규모로 추정, 미측정).

**결정**

## D-036 — CLI loop 는 실패하면 재시도하고, reviewer 의 FAIL 사유를 다음 사이클에 싣는다 (L2 + L4)

**배경**
CLI 의 loop 는 `recover: () => 'abort'` 라 **1사이클짜리**였다 — PASS 면 goal-reached, FAIL 이면 aborted. `maxIterations`(8) 에 닿을 길이 없었고, 실행 전 "최대 8사이클 · 최악 $…" 안내도 부풀려진 값이었다. 그렇다고 retry 로만 바꾸면 **눈먼 재시도**다: reviewer 프롬프트가 "PASS/FAIL 만 한 줄" 이라 사유가 생성조차 되지 않고, Planner 는 2사이클부터 "직전 사이클의 지적을 반영하라" 만 붙였다. 또 판정 정규식 `/\bPASS\b/i` 는 사유 텍스트 속 PASS 에도 매치된다. 별개로 Evaluator 과금은 추정 금액만 적고 토큰을 세지 않아 D-035 토큰 상한이 reviewer 몫을 빼먹었다.

**결정**
1. **(L2)** CLI loop 는 검증 FAIL 이면 `retry` — `maxIterations`·금액·토큰 상한까지 돈다. Core `runLoop` 의 기본값(recover 미지정 = abort)은 그대로 둔다. 예전 동작은 `--max-iterations 1` 로 똑같이 얻는다 — 그래서 `--recover` 옵션(L3)은 만들지 않는다.
2. **(L4)** reviewer 는 **첫 줄에 PASS 또는 FAIL 만**, FAIL 이면 둘째 줄부터 부족한 점을 적는다. 그 사유는 `LoopContext.feedback` 으로 다음 사이클의 Planner 에 넘어가고, CLI Planner 는 이를 프롬프트에 싣는다.
3. 판정은 **첫 줄 엄격 일치**로 읽는다(마크다운 강조 기호는 허용). 형식을 어기면 FAIL 로 본다 — 모르면 통과가 아니다(fail-closed).
4. reviewer 실행 자체가 실패하면(`ok: false`) 재시도하지 않고 `escalate` 한다 — 망가진 엔진에 primary 를 반복해서 태우지 않는다.
5. Evaluator 도 Executor 와 같은 우선순위(actual > metered > estimate)로 과금하고 토큰을 센다. `Verdict.cost` 로 실행 결과를 돌려받는다.

**규모** (추정 — D-035 와 같은 근거, 실측 아님): 1사이클 ≈ 34만 토큰. 기본 상한 200만이면 재시도 포함 약 5~6사이클에서 멈춘다. reviewer 토큰을 세기 시작하므로 이전 추정보다 조금 일찍 멈출 수 있다.

**기각**
- *L1 abort 유지 + 문서화* — loop 가 pipeline(실행 + 리뷰 1회)과 사실상 같아진다.
- *L2 단독* — 사유 없는 재시도는 같은 실수를 반복하며 토큰만 쓴다.
- *L3 `--recover` 옵션* — abort 는 `--max-iterations 1` 로 이미 된다. 옵션 표면만 는다.
- *직전 산출물도 Planner 에 싣기* — `--write` 에서는 작업 트리에 이미 남아 있다. 쓰기 없는 모드의 이득은 실측이 없어 열지 않는다.

**영향**
CLI loop 가 실패 시 여러 사이클을 돈다 — 실패 경로가 이전보다 비싸지만 상한(D-017·D-035) 안에서다. 판정 형식이 바뀌어 reviewer 가 형식을 어기면 통과가 FAIL 로 뒤집힐 수 있다(의도된 방향).

**상태** 확정 — 2026-09-24 사용자 결정 (L2 + L4).
