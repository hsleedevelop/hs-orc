## D-001 — v1은 TUI, v2는 GUI

**배경**
초기 스케치가 "tui or gui"로 열려 있었다.

**결정**
1차 릴리스는 TUI. GUI는 v2로 미룬다.

**근거**
오케스트레이터가 띄우는 대상(`claude`, `codex`, `cursor-cli`)이 전부 터미널 CLI다. 같은 터미널에 사는 편이 배포·통합이 단순하다. GUI가 실질적으로 나은 부분(dashboard, 그래프 시각화)은 코어가 안정된 뒤에 붙여도 늦지 않다.

**영향**
**Core(분류·라우팅·어댑터·진행 방식)는 UI를 모르는 헤드리스 라이브러리여야 한다.** v2에서 Shell만 교체한다. `core/`가 `shell/`을 import하면 lint 에러가 나게 경계를 강제한다. v2에서 Core 수정이 필요하면 v1 설계가 틀린 것이고, 그 경우 GUI를 진행하지 말고 경계를 먼저 고친다.

**상태** 확정

## D-002 — 진행 방식 3종의 의미론

**배경**
`/pingpong`, `/loop`, `/graph` 중 이 환경에 존재하는 것은 `/loop`(Claude Code 내장 스킬)뿐이다. 나머지 둘은 호출하면 되는 기존 기능이 아니라 이 제품이 정의할 대상이었다.

**결정**

| 방식 | 성격 | 자율성 |
|---|---|---|
| `/pingpong` | 대화형 | **비자율** — 사용자가 매 턴 개입 |
| `/loop` | loop-engineering | 자율 반복 |
| `/graph` | graph-engineering | 자율 DAG |

**근거**
세 방식을 같은 축(자율성)으로 갈라야 상한 정책이 일관된다. pingpong은 매 턴 사용자 승인이 있으므로 턴 제한이 불필요하고, loop와 graph는 사람이 안 보는 동안 도니까 상한이 **필수**다.

**영향**
- `/pingpong`: 1턴 = 1작업. 턴 종료 시 결과·다음 제안을 제시하고 사용자 입력을 기다린다. 최대 턴 제한 없음, 누적 비용 상시 표시.
- `/loop`: Goal · Planner · Executor · Evaluator · Critic · Recovery · Stop을 분리된 구성요소로. **최대 반복 수 없이는 구현하지 않는다.**
- `/graph`: 노드별 독립 배정, 실행 전 순환 검출 필수, 병렬은 쓰기 대상 비겹침 확인 시에만, 부분 실패 전파 규칙을 노드마다 선언.
- 세 방식 공통으로 **상한 도달 시 정상 중단을 정상 완료보다 먼저 검증한다.**

**상태** 확정 (단, `/pingpong`의 "대화형"이 사용자와의 대화라는 해석은 확인 대기 — D-006)

## D-003 — `/loop`의 Evaluator에 reviewer 슬롯 모델을 쓴다

**배경**
매트릭스는 모든 행에 independent reviewer를 둔다. 자율 루프에서 이 reviewer가 어디에 들어가는지가 정해지지 않았다.

**결정**
`/loop`의 Evaluator 역할에 매트릭스의 reviewer 슬롯 모델을 배정한다.

**근거**
Evaluator는 "결과가 기준을 충족했는가"를 판정하는 자리다. 이것을 primary와 같은 모델이 하면 자기 채점이 된다. 매트릭스가 요구하는 독립 리뷰가 루프 안에서 실현되는 유일한 자리다.

**영향**
루프 1사이클 비용 = primary 1회 + reviewer 1회. 비용 산정과 상한 계산이 이를 반영해야 한다.

**상태** 확정

## D-004 — `cursor-cli -p`는 전역 대체가 아니라 모델별 대체다

**배경**
초기 스케치는 엔진으로 claude / codex / cursor-cli 셋을 들었으나, 매트릭스 11행 어디에도 Cursor 모델이 없다. Cursor의 역할이 정의되지 않은 상태였다.

**결정**
`cursor-cli -p`를 **대체 하네스**로 둔다 — 매트릭스가 배정한 모델을 다른 하네스로 돌리는 경로다. 단 **모델별로만** 성립한다.

**근거 (실측, 2026-09-20 `cursor-agent --list-models`)**

| 매트릭스 모델 | Cursor 커버 |
|---|---|
| Luna / Terra / Sol | `gpt-5.6-{luna,terra,sol}-{effort}` ✅ |
| Sonnet / Opus / Fable | `claude-{sonnet-5,opus-5-thinking,fable-5-1}-{effort}` ✅ |
| **Astra** | **없음** ❌ |
| **Haiku** | **없음** ❌ |

8모델 중 6개만 커버한다. Astra는 11행 중 6행(primary 4·reviewer 2)에, Haiku는 1행의 reviewer에 등장하므로 전역 대체는 성립하지 않는다.

**영향**
`engines.json`에 모델별 가용성 테이블을 둔다. `supports()`가 이를 읽고, 지원하지 않는 조합에 대체를 시도하면 **명시적 실패**다 — 가장 가까운 모델로 말없이 바꾸지 않는다.

**상태** 확정

## D-005 — 바이너리 이름은 `cursor-cli`, 해석은 폴백으로

**상태** 확정

## D-006 — `/pingpong`의 "대화형" 해석 (확인 대기)

**배경**
"대화형"이 **사용자와의 대화**인지 **primary↔reviewer의 교대**인지 두 가지로 읽힌다.

**현재 해석**
사용자와의 대화 — 사용자가 매 턴 개입하는 human-in-the-loop 진행.

**근거**
다른 두 방식을 "loop-engineering", "graph-engineering"이라는 규율 이름으로 부른 것과 달리 `/pingpong`만 성격("대화형")으로 불렀다. 자율/비자율 축에서 유일한 비자율 방식으로 두면 세 방식이 서로 겹치지 않는다.

**뒤집힐 경우의 영향**
primary↔reviewer 교대라면 **자율 실행**이 되므로 최대 왕복 수, 수렴 판정 기준, 교착 시 중단 조건이 전부 필수가 된다. 상한 정책이 D-002와 달라진다.

**상태** 확인 대기

## D-007 — `/loop`는 자체 구현 (기본안)

**배경**

**결정 (기본안)**

**상태** 기본안 — S4 착수 전 확정 필요

## D-011 — effort 검증은 어댑터에서 **던진다**

**배경**
세 엔진의 effort 표기가 전부 다르다.

**결정**
정규 어휘 `low | medium | high | xhigh | max`를 두고, 어댑터가 CLI에 넘기기 **전에** 검증해 밖의 값이면 예외를 던진다. 조용한 기본값 폴백을 만들지 않는다.

**근거 (실측, 2026-09-20)**
`claude -p --effort bogus` 실행 시 출력: `Warning: Unknown --effort value 'bogus' — ignoring it and using the default effort.` **경고만 내고 기본 effort로 실행된다.** 잘못된 effort로 돌아도 아무도 모르므로 어댑터 사전 검증이 유일한 방어선이다.

**영향**
| 정규값 | claude | codex | cursor |
|---|---|---|---|
| low~max | `--effort <v>` | `-c model_reasoning_effort="<v>"` | 모델 id 접미사 `-<v>` |

codex의 `ultra`는 매트릭스에 없으므로 정규 어휘에 넣지 않는다. 매트릭스의 `Mid`는 `medium`으로 매핑한다.

**상태** 확정

## D-015 — `/pingpong`의 "대화형"은 사용자와의 대화다 (Q1 확정)

**배경**
D-006이 두 해석을 열어 두었다. ① 사용자와의 대화(human-in-the-loop) ② primary↔reviewer 자율 교대.

**결정**
①이다. 매 턴 **사용자 입력을 기다린다.** 따라서 최대 턴 수 제한을 두지 않는다 — 상한의 역할을 사용자 승인이 대신한다. primary와 reviewer를 같은 턴 안에서 교대로 붙일 수는 있으나, 그 교대를 **자동으로 반복하지 않는다.**

**근거**
②로 가면 pingpong이 사실상 두 번째 loop가 되고, 최대 왕복 수·수렴 판정·교착 중단이 전부 필수가 되어 D-002(자율성으로 방식을 가른다)가 무너진다. 사용자 결정(2026-09-20).

**영향**
`/pingpong`만 비자율이므로 턴 상한 대신 **누적 비용 상한**만 공유한다. 상한 도달 시 다음 턴을 시작하지 않고 사람에게 올린다.

**상태** 확정 — Q1 종결

## D-017 — 누적 비용 상한 기본값은 $20 (Q3 확정)

**배경**
자율 방식(`/loop`, `/graph`)은 무한 반복이 곧 비용이다. 상한이 없으면 사고가 난다.

**결정**
누적 비용 상한 기본값 **$20**. `data/limits.json`에 두고 사용자가 덮어쓸 수 있다.

**근거**
매트릭스 최고 조합(Fable+Astra $10.89)으로 **2사이클을 돌면 상한에 닿는다.** 사고가 나도 한 자릿수 사이클에서 멈추고, 정상 작업이 상한에 걸리면 그것 자체가 "이 작업은 방식이 틀렸다"는 신호가 된다. 사용자 결정(2026-09-20).

**영향**

## D-019 — Ink을 쓰되 JSX는 쓰지 않는다

**배경**
Node 25의 타입 스트리핑은 **JSX를 처리하지 못한다.** JSX를 쓰려면 빌드 단계(esbuild/tsc emit)를 추가해야 하고, 그러면 테스트 실행 방식(`node --test` 로 `.ts` 직접 실행)까지 바뀐다.

**결정**
화면은 `createElement`(`el` 헬퍼)로 작성하고 **빌드 단계를 추가하지 않는다.** 대신 화면 로직을 **뷰모델(순수 `.ts`)로 분리**하고 Ink 렌더 층은 얇게 유지한다.

**근거**
렌더 층이 얇으면 JSX의 이득이 작고, 빌드 단계는 S0에서 세운 게이트(타입 스트리핑 기반 `node --test`)를 통째로 바꾼다. 뷰모델 분리는 Core가 UI를 모른다는 원칙(D-001)과도 같은 방향이고, 테스트가 터미널을 띄우지 않아도 된다.

**영향**
화면이 커져 `createElement` 중첩이 읽기 어려워지면 그때 esbuild를 도입한다 — **그 전까지는 렌더 층이 얇지 않다는 신호로 읽는다.**

**개정 2026-09-21 (S7)** — 탈출구를 **렌더러에만** 열었다. Electron 렌더러는 Chromium이라 TS도 bare specifier도 못 읽어 번들러 없이는 React가 아예 안 뜬다(선택이 아니라 제약). 그래서 `esbuild`로 `src/shell/gui/renderer/` 하나만 묶고, 메인 프로세스와 TUI는 타입 스트리핑 그대로 둔다. **번들러가 생겼어도 JSX는 여전히 안 쓴다** — 두 셸의 화면 코드가 같은 모양이어야 v1↔v2 이식을 눈으로 대조할 수 있다. 렌더러는 DOM lib이 필요해 `tsconfig.renderer.json`으로 갈라 타입 검사한다(게이트는 두 tsc를 모두 돌린다).

**상태** 확정

## D-024 — 진입점은 `.mjs` 래퍼 하나이고 빌드 산출물을 만들지 않는다

**배경**
v1~v2 내내 실행 경로가 `npm run` 뿐이었다 — 이 저장소 안에서만 돈다. 라우터는 **작업 중인 다른 프로젝트**에서 불려야 쓸모가 있다.

**결정**
`bin/hs-orc.mjs` 하나를 `package.json` 의 `bin` 으로 노출하고, 이 파일이 `src/shell/` 의 `.ts` 를 **그대로** 띄운다. `dist/` 를 만들지 않는다(D-019). 래퍼 자신만 `.mjs` 다 — 진입점은 타입 스트리핑 없이 떠야 하기 때문이다.

- `hs-orc "<작업>"` → `src/shell/cli.ts` · `hs-orc tui` → `tui/main.ts` · `hs-orc gui` → 렌더러 번들 → `electron gui/main.ts`
- cli·tui 는 **하위 프로세스를 더 띄우지 않는다.** `process.argv` 만 실제 호출 모양으로 바꾸고 `import()` 한다 — 래퍼가 한 겹 끼면 TUI 의 raw mode 와 엔진 프로세스 그룹 종료(SPEC §3)가 그만큼 멀어진다.
- `npm run tui|gui|build:gui` 도 이 래퍼를 부른다. 실행 경로를 둘로 두지 않는다.

**경로 해석은 두 기준으로 갈리고, 그게 의도다**

| 대상 | 기준 | 이유 |
|---|---|---|
| `data/{matrix,engines,limits,verify}.json` | **설치 위치** (`import.meta.dirname`) | 어디서 부르든 같은 매트릭스여야 한다 |
| `.hs-orc/runs`, `.hs-orc/unclassified.jsonl` | **cwd** | 실행 산출물은 작업 중인 프로젝트에 쌓여야 한다 |
| 결정 로그 | `~/.claude/logs/` (`HS_ORC_DECISION_LOG` 로 분리) | 프로젝트를 가로지르는 기록이다 |

한쪽이 뒤집히면 "다른 디렉터리에서 쓸 수 있다"가 조용히 거짓이 되므로 `src/shell/__tests__/bin.test.ts` 가 프로세스 수준에서 고정한다.

**타입 스트리핑은 capability 로 판정한다.** `process.features.typescript` 를 보고 꺼져 있으면 즉시 던진다. Node 버전 표를 코드에 적지 않는다 — 표는 낡고, 낡은 표는 조용한 오진이 된다.

**상태** 확정 — 2026-09-21 실측

## D-025 — 쓰기 권한은 primary 슬롯만, 그것도 명시적 옵트인

**배경**
진입점 실사용에서 **primary(codex)가 read-only 샌드박스로 떠서 파일을 못 고쳤다.** "수정안"만 내고 끝났고 reviewer 가 그것을 FAIL 로 잡았다. 두 슬롯 설계는 작동했지만, 라우터가 광고하는 "실행"이 실제로는 안 되고 있었다.

**결정**

1. **`engines.json` 에 엔진별 쓰기 인자를 선언한다.** 실측 `--help` 기준이고, 워크스페이스 밖까지 여는 값은 선언하지 않는다.

   | 엔진 | 쓴다 | 쓰지 않는다 |
   |---|---|---|
   | codex | `-s workspace-write` | `danger-full-access` |
   | claude | `--permission-mode acceptEdits` | `bypassPermissions` (쉘까지 열린다) |
   | cursor | `--force` | `--yolo` (같은 것의 별칭) |

2. **reviewer 는 절대 받지 않는다.** `ResolvedSlot` 에 `role` 을 두고 `core/executor.ts` 한 곳에서 `options.write === true && slot.role === 'primary'` 로만 부여한다. 호출자가 무엇을 넘겨도 reviewer 는 읽기 전용이다. 판정 대상을 스스로 고칠 수 있는 검증자는 독립 검증자가 아니다 (D-003·INV-1).

3. **기본은 꺼짐, `--write` 로 옵트인.** PLAN "사람에게 올리는 조건"에 **외부 쓰기**가 있다. `--run` 이 비용 승인이라면 `--write` 는 쓰기 승인이고, 둘은 다른 결정이다. 쓰기 여부는 **승인 전 화면에 비용과 나란히** 찍는다.

4. **선언이 없는 엔진에 쓰기를 요청하면 던진다.** 읽기 전용으로 조용히 떨어뜨리면 아무것도 안 바꾼 산출물이 "고쳤다"로 통과한다 — hs-00-core 가 금지하는 조용한 폴백이다.

**기각**
- *기본을 켜짐으로* — `--run` 하나로 비용과 파일 수정을 동시에 승인하게 된다. 되돌리기 어려운 쪽을 끼워 파는 셈이다.
- *`bypassPermissions` / `danger-full-access`* — 워크스페이스 밖 쓰기와 임의 쉘이 열린다. 얻는 것(프롬프트 0회)에 비해 잃는 것이 크다.
- *reviewer 에게도 쓰기* — "reviewer 가 직접 고치면 빠르다"는 유혹이 있으나, 그 순간 산출물과 판정의 출처가 같아져 D-009 의 두 슬롯이 무의미해진다.

**실측 (2026-09-21, `/tmp` 빈 git repo)**
`hs-orc "broken.ts 의 타입 에러를 고쳐라" --write --run` → Luna(codex)가 **파일을 실제로 수정**(`git diff` 1 file changed, `number` → `string`), Haiku(reviewer)는 `tsc 실행 권한 미획득`을 사유로 들며 `FAIL` — reviewer 가 읽기 전용으로 남았다는 실증이다. `--write` 없이는 종전대로 수정안만 낸다.

## D-026 — LLM 분류 폴백은 기본으로 돈다, 대신 돌았다고 말한다 (Q8 확정)

**배경**
규칙 표(`core/classify.ts`)는 행별 키워드 몇 개에 의존한다. 실사용 첫 작업 "…켤 수 있게 하라" 가 R03 키워드(`구현해`·`만들어`)에 안 걸려 **그냥 실패했다**(PLAN S9-2). 명령형 어미 하나 차이로 제품이 멈춘다.

**결정**
`--classify-llm` 을 **기본 켜짐**으로 바꾸고 `--no-classify-llm` 으로 끈다. 폴백이 돌면 **반드시 한 줄을 찍는다**: `분류 규칙 무매치 → Haiku·low 로 분류만 재시도 (+$0.001 내외 · --no-classify-llm 으로 끈다)`.

- **말없이 도는 유료 호출은 없다.** 기본을 켜는 대가로 비용 표기를 의무화한다 — SPEC §7 "실행 전 비용 표시" 를 분류 단계까지 넓힌 것이다.
- **폴백 실패는 삼키지 않는다.** 바이너리가 없거나 호출이 실패하면 `[notice][pipeline/classify-fallback]` 을 찍고 미분류 경로로 내려간다. 폴백이 죽어도 전체가 죽지는 않되 침묵하지도 않는다.
- 옛 `--classify-llm` 플래그는 **계속 받는다**(이제 무해한 명시). 지우면 기존 스크립트에서 그 낱말이 **작업 문자열로 섞여 들어간다.**
- 곁다리로 같은 구멍을 막았다: **모르는 `--옵션` 은 던진다.** 전에는 `--오타` 가 조용히 작업 문자열의 일부가 됐다.

**기각**
- *키워드 표를 넓힌다* — 어미·표현이 무한해 두더지잡기다. 표가 커질수록 왜 그 행으로 갔는지 설명하기도 어려워진다.
- *현상 유지(기본 꺼짐)* — "돈 나가는 호출은 전부 옵트인" 원칙은 맞지만, 분류 1회는 $0.001 규모이고 그 대가가 **평범한 문장에서의 실패**다. 비용 표기로 원칙의 실질(사용자가 알고 쓴다)을 지킨다.

**세 셸이 같은 함수를 쓴다** — `core/pipeline.ts` 의 `routeWithFallback`. 처음에는 CLI 안에 인라인으로 뒀는데, 그러면 셸마다 복제되거나(세 벌) 한쪽에만 있어 **같은 입력이 다르게 동작한다.** 그래서 폴백을 Core 로 올리고 인라인을 지웠다. 셸은 `fallback.line` 을 자기 방식으로 그릴 뿐이다(CLI 는 stderr, TUI·GUI 는 뷰모델 `notes`).

이 때문에 TUI 의 `RunScreen` 과 GUI 의 `plan()` 이 **비동기**가 됐다. 렌더 중 동기 라우팅은 더 이상 못 한다 — 그 대가로 셸 간 동작 차이가 없다.

**분류는 결정적이지 않다.** 같은 문장이 S9 에서는 R01, D-026 실측에서는 R03 으로 갔다. 폴백은 "무엇이든 고른다" 가 아니라 "고른 근거를 표기한다"(`Haiku·low 분류 R03`)로 정직해진다.

## D-027 — 단가는 선언으로 받고, 근거 등급을 하나 더 만든다

**배경**
`claude` 만 `total_cost_usd` 를 돌려준다. codex·cursor 는 **토큰만** 주므로 단가표가 없으면 AA 벤치마크 추정치로 누적된다. 그런데 토큰은 이미 파싱돼 있다 — 단가만 있으면 훨씬 정확해진다.

**결정**

1. **`data/pricing.json` 에 모델 id 별 단가를 선언한다.** `verify.json` 과 같은 방식이다 — **제품은 단가를 추측하지 않는다.** 저장소 기본값은 **비어 있다.**
2. **출처를 셋으로 나눈다.** 우선순위는 `actual` > `metered` > `estimate` 다.

   | 출처 | 뜻 |
   |---|---|
   | `actual` | 엔진이 돌려준 값 (`total_cost_usd`) |
   | `metered` | 엔진이 보고한 **측정 토큰** × **선언 단가** |
   | `estimate` | 매트릭스의 AA 벤치마크 작업당 비용 |

   `metered` 를 `actual` 이라 부르지 않는다 — **벤더가 청구한 금액이 아니다.** 측정치와 선언값의 곱이고, 단가가 틀리면 결과도 틀린다. 이름이 그 차이를 지고 있어야 한다.
3. **섞이면 무엇이 섞였는지 누적 표시에 적는다**: `$1.2340 / $20 (실측+토큰×선언단가)`.
4. **선언이 없는 모델은 `undefined` 다. 0 이 아니다.** 0 으로 떨어뜨리면 "공짜로 돌았다" 가 되어 누적 비용과 상한이 통째로 거짓이 된다.

**기각**
- *단가를 코드에 박는다* — 모델·가격은 바뀌고, 틀린 단가로 계산한 "실비" 는 추정치보다 나쁘다(정확해 보이기 때문이다).
- *`metered` 를 `actual` 로 합친다* — 두 값의 신뢰도가 다르다. SPEC §2.5 가 근거 등급을 섞지 말라고 한 것과 같은 이유다.
- *단가가 없으면 추정치로 조용히 대체* — 이미 그렇게 한다. 다만 **어느 쪽인지 표시**하는 것이 이 결정의 핵심이다.

**상태** 확정 — 2026-09-21. 단가표 자체는 비어 있다: 실제 값은 쓰는 사람이 자기 요금제로 채운다.

## D-028 — 워크트리는 저장소 안이 아니라 홈에 둔다

**배경**
`--write`(D-025)를 켜면 primary 슬롯이 파일을 고친다. 그 대상이 **지금 사람이 편집 중인 작업 트리**면 되돌리기가 사람 몫이 된다. GUI 에 git worktree 를 붙이기로 하면서 "어디에 만들 것인가" 가 갈렸다.

**결정**

1. **위치는 `~/.hs-orc/worktrees/<저장소>/<이름>` 이다.** 저장소 밖이다. `HS_ORC_WORKTREES` 로 뿌리를 옮길 수 있다.
2. **저장소 폴더 이름에 실제 경로 sha256 앞 8자를 붙인다** (`hs-orc-ba831a89`). 이름만 쓰면 서로 다른 저장소의 `api` 두 개가 같은 자리를 노린다.
3. 브랜치는 `hs-orc/<이름>` 이고, **만들면 그 안으로 바로 들어간다.** 만들고 본체에 남으면 쓰기를 가둔 뜻이 없다.
4. 삭제는 `--force` 를 쓰지 않는다. 커밋 안 한 변경이 있으면 git 이 거절하고 그 말을 그대로 올린다. 브랜치는 `git branch -d`(머지된 것만)로만 지우고, 거절당하면 **남기고 그렇다고 말한다.**
5. **새 워크트리에는 의존성이 따라오지 않는다 — 실행 전에 알린다.** `node_modules` 가 없으면 검증 명령도, primary 가 스스로 돌리는 test 도 성립하지 않는다. 첫 실사용에서 primary 가 실제로 여기서 막혔다(그것도 **돈을 쓴 뒤에**). 세 셸이 같은 감지기(`shell/deps.ts`)를 쓰고, **설치를 대신 해 주지는 않는다** — 네트워크와 시간이 드는 일이라 사람이 결정한다(D-022 의 "제안만 한다" 와 같은 정신). lock 파일이 있으면 `npm ci` 를 제안한다: 워크트리의 의존성 버전이 본체와 갈리면 검증이 거짓이 된다.
6. **실행 기록이 남아 있으면 삭제를 거절한다.** 산출물은 cwd 기준으로 쌓이므로(`bin/hs-orc.mjs`) 워크트리를 지우면 그 안의 `.hs-orc/runs/` 도 같이 사라진다. "증거로 종료" 하는 제품이 증거를 조용히 버리면 안 된다 — **2026-09-22 에 첫 실사용의 원시 로그를 실제로 이렇게 잃었다**(브랜치를 지우는 도구가 워크트리까지 함께 제거했다). git 이 dirty 를 거절하는 것과 같은 자리에서 같은 방식으로 막는다.

**근거**
저장소 안(`<repo>/.hs-orc/worktrees/`)에 두면 세 가지가 따라온다: 프로젝트마다 무시 설정을 강요하고, 검색·빌드·감시 도구가 저장소를 재귀로 훑고, 워크트리 안에 워크트리가 중첩된다. **ao 도 같은 이유로 홈(`~/.ao/data/worktrees/<repo>/`)에 둔다** — 같은 문제를 먼저 겪은 도구의 선택이다.

이것은 `bin/hs-orc.mjs` 가 못 박은 두 기준에 **세 번째를 더한다.**

| 기준 | 무엇 |
|---|---|
| 설치 위치 | `data/*.json` — 어디서 부르든 같은 매트릭스다 |
| cwd | `.hs-orc/runs`, `.hs-orc/unclassified.jsonl` — 산출물은 작업 중인 프로젝트에 쌓인다 |
| **홈** | **워크트리, 최근 프로젝트 목록 — 프로젝트를 건너다니는 사용자의 상태다** |

**기각**
- *저장소 안 `.hs-orc/worktrees/`* — 위 세 가지. 첫 구현이 여기였고, 실제로 저장소가 지저분해졌다.
  가상의 우려가 아니다: **이 저장소 자신이 그렇게 돼 있었다.** 다른 에이전트 도구가 `.claude/worktrees/` 에 워크트리 두 개를 만들어 뒀고, 무시 설정이 없어 415MB 가 `git add .` 한 번 거리에 놓여 있었다(2026-09-22 `.gitignore` 에 추가).
- *형제 폴더 `../<repo>-<이름>`* — 부모 디렉터리에 쓰는 것은 권한도 관례도 불확실하다. iCloud 동기화 폴더 안이면 더 나쁘다.
- *`git worktree remove --force`* — 편하지만 커밋 안 한 남의 작업을 말없이 버린다. 거절하고 사유를 보여주는 편이 낫다.

**영향**
`.hs-orc/` 라는 이름이 **두 자리에 있다** — cwd 아래(실행 산출물)와 홈 아래(워크트리·최근 목록). 같은 이름이 다른 뜻으로 쓰이므로 헷갈릴 수 있어 여기 적어 둔다. 판별 기준은 "이 데이터가 프로젝트의 것인가, 사람의 것인가" 다.

**상태** 확정 — 2026-09-21. GUI 실측으로 생성→삭제 왕복 확인(워크트리·브랜치·홈 폴더·최근 목록 정리, 같은 저장소의 다른 도구 워크트리 무영향).

## D-029 — 작업 폴더 전환은 GUI 에만 둔다

**배경**
GUI 를 `process.cwd()` 에서 떼어내면서, CLI·TUI 에도 같은 전환을 줄지가 남았다.

**결정**
**전환은 GUI 만 한다.** CLI·TUI 는 `process.cwd()` 고정이고, `--cwd` 같은 옵션을 만들지 않는다.

**근거**
**셸이 이미 폴더를 고르는 도구다.** CLI 에 `--cwd` 를 더하면 폴더의 진실이 둘이 되고(`cd` 한 자리 vs 플래그), 어느 쪽이 이겼는지 매번 설명해야 한다. TUI 도 같은 터미널에 산다.

**GUI 만 셸이 없다.** 아이콘으로 띄우면 cwd 가 무엇인지 사용자가 알 길이 없고, 그 상태로 `--write` 를 켜는 것이 이 제품에서 가장 위험한 조작이다. 전환 UI 는 그 공백을 메우는 것이지 편의 기능이 아니다. 화면에 폴더가 **항상 보이는** 것이 전환 기능 자체보다 중요하다.

**기각**
- *세 셸 전부에 `--cwd`* — 위. 그리고 CLI 에서 그 플래그를 쓸 이유가 `cd` 말고 없다.
- *Core 에 전역 작업 폴더를 둔다* — Core 가 UI 상태를 갖게 된다. D-001 이 막은 방향이다.

**영향**
`GuiService.workdir` 가 작업 폴더의 **유일한 소유자**다. 이 클래스 안에서 `process.cwd()` 를 다시 읽는 곳이 생기면 화면의 폴더와 실행 폴더가 갈린다 — 가장 위험한 종류의 버그라 테스트로 고정했다.

분류기(`core/classify-llm.ts`)도 같은 폴더에서 돈다. 처음에는 여기만 `process.cwd()` 로 남아 있었다(Q9) — 읽기 전용이라 오동작은 아니지만 **화면이 말하는 폴더와 실제로 띄운 폴더가 갈린다.** `cwd` 를 `routeWithFallback` 의 옵션으로 올려 GUI 만 넘긴다. 기본값이 `process.cwd()` 라 CLI·TUI 는 그대로다.

**이것은 D-001 위반이 아니다.** Core 가 UI 를 아는 것이 아니라, **숨어 있던 전역 의존(`process.cwd()`)을 인자로 드러낸 것**이다. 방향이 반대다 — Core 는 더 순수해졌다.

**상태** 확정 — 2026-09-21. Q9 는 2026-09-22 에 닫았다.

## D-030 — 요금제는 선언으로 받고, 상한은 청구되는 것에만 건다

**배경**
D-027 이 근거 등급을 셋으로 나눴다: `actual`(엔진이 돌려준 값) > `metered`(측정 토큰 × 선언 단가) > `estimate`(AA 벤치마크). 이 순서의 근거는 **"벤더가 청구한 금액에 얼마나 가까운가"** 였다.

그 전제가 틀렸다. 이 저장소를 쓰는 사람은 claude·codex·cursor 를 **전부 구독제**로 쓴다. 구독제에서는 claude 가 주는 `total_cost_usd` 조차 청구되지 않는다 — API 로 썼다면 들었을 환산액이다. 세 등급이 전부 같은 배를 타고 있었고, **D-017 의 누적 상한 $20 은 아무것도 막지 않고 있었다.**

**결정**

1. **요금제는 엔진별 선언이다** (`engines.json` 의 `plan: "subscription" | "api"`). 제품이 알아낼 수 없다 — 같은 CLI 를 구독제로도 API 키로도 쓴다. 타입에서 **필수**다: 빠지면 금액 표시가 청구인지 환산인지 말할 수 없다.
2. **슬롯이 자기 요금제를 들고 다닌다** (`ResolvedSlot.plan`). 그래야 `Budget` 이 카탈로그를 몰라도 된다.
3. **금액 상한은 `billedUsd`(api 요금제 charge 합)에만 건다.** 구독제 환산액은 `convertedUsd` 로 따로 센다. 둘을 합친 `spentUsd` 는 **표시용이고 상한 판정에 쓰지 않는다.**
4. **구독제에서 막는 것은 토큰이다** (`limits.json` 의 `tokenBudget`, 기본 200만). 실제로 희소한 자원은 돈이 아니라 사용량 한도(주간·5시간 rate limit)이고, 그에 비례하는 것이 토큰이다.
5. **두 상한 중 하나라도 닿으면 멈춘다** — `Budget.limitReached()`. 실행을 멈출지 묻는 곳은 전부 이것을 쓴다. `exceeded()`(금액)만 보면 구독제에서 아무것도 막지 못한다.
6. **토큰을 보고하지 않은 사이클은 0 으로 채우지 않는다.** 따로 세어(`unreportedCycles`) 누적 표시에 드러낸다 — 0 으로 떨어뜨리면 "공짜로 돌았다" 가 되어 상한이 통째로 거짓이 된다 (D-027 의 `undefined` 규칙과 같은 이유).
7. **표시가 거짓말하지 않는다.** 전부 구독제면 `$0.2730 API 환산 · 구독제라 청구되지 않는다 · 토큰 12345/2000000` 이다. `/ $20` 을 붙이면 그 상한이 이 숫자를 막는다는 거짓말이 된다.

**기각**
- *상한을 아예 끈다* — D-017 이 "자율 방식은 무한 반복이 곧 비용" 이라 적은 근거를 포기하는 선택이다. 구독제에서도 무한 반복은 한도를 태운다.
- *사이클 수로 센다* — 구현은 가장 쉽지만 R01 한 번과 R11 한 번을 같게 세어 실제 소모와 많이 어긋난다.
- *전역 요금제 선언 하나* — 엔진마다 요금제가 다를 수 있다(한쪽만 API). 거짓이 되는 순간이 온다.
- *`metered` 를 아예 끈다* — 청구되지 않아도 **배정 간 상대 비교**에는 그대로 쓸모 있다. 첫 실사용에서 R03 $7.08 vs R01 $0.39 라는 18배 차이를 보고 배정을 내린 그 판단이 그것이다.

**영향**
**1단계(표시만 고치기)와 2단계(토큰 상한)를 나눌 수 없었다.** 금액 상한을 청구분에만 거는 순간 구독제 사용자에게 상한이 사라지고, 그것은 `limits.json` 의 "상한이 없는 방식은 머지하지 않는다"(PLAN S4) 위반이다. 실제로 1단계만 넣었을 때 상한 테스트 3건이 곧바로 빨간불이 됐다 — 쪼개려던 계획을 그 실패가 막았다.

`SlotRun` 에 `usage` 가 생겼다. `rawStdout`(SPEC §3.7)에 이어 두 번째 경계 확장이고, 이유도 같다: **어댑터가 이미 알고 있는 것을 셸까지 내려보내지 않으면 상한도 단가도 거짓이 된다.**

**상태** 확정 — 2026-09-22. 음성 대조: `limitReached()` 를 `exceeded()` 로 되돌리면 토큰 상한 테스트 3건이 전부 실패하고, 원복하면 통과한다.

## D-031 — 제품 단위를 "작업 1건"에서 "대화 세션"으로 올린다 (지휘자 층)

**배경**
첫 GUI 실사용(2026-09-23)에서 "넌 누구니" 를 전송하자 **아무 일도 일어나지 않았다.** 분류 실패 → 승인 버튼 없음 → 끝. 원인은 화면이 아니라 제품 정의에 있었다.

- PRD §2 는 제품을 **작업 1건 라우터**로 정의했다. 채팅·세션·결과 처리가 요구사항 어디에도 없다.
- §1 하한선의 "직접 처리" 는 원래 Claude Code 세션 안에서 delegation-router 를 쓸 때 **"메인 세션인 내가 한다"** 는 뜻이다. 이 제품은 라우터만 옮겨 오고 **그 "나" 를 옮겨 오지 않았다** — 그래서 `direct` 는 "엔진을 띄우지 않는다" 로 끝나고 아무도 답하지 않는다.
- 유일한 대화형인 `/pingpong` 은 CLI 에만 있고, **세션 시작 때 배정 1회로 고정**되며, 매 턴이 새 비대화 실행이라 **맥락이 이어지지 않는다** (`core/modes/pingpong.ts` — `execute(slot, prompt)` 뿐, 어댑터에 resume 경로 없음).

사용자가 원한 것은 **프로젝트(또는 스크래치)로 들어가 orc 채팅창에 요청하면, orc 가 모델·effort 를 정해 위임하고 결과를 받아 처리하는** 제품이다. 진입·세션 모양은 AO(`Untrivial-ai/agent-orchestrator`)를 참조한다.

**결정**

1. **진입 단위는 세션이다.** 세션은 둘 중 하나로 시작한다.
   - `project` — 폴더 기준. D-029 의 폴더·워크트리 전환을 그대로 쓴다.
   - `scratch` — 폴더 없이 시작하는 단일 세션. 엔진이 cwd 를 요구하므로 `~/.hs-orc/scratch/<id>/` 를 만든다. git 이 아니고 **쓰기는 기본 꺼짐**이다.
2. **세션의 진실은 orc 가 가진 대화 기록이다.** append-only (`<세션 폴더>/.hs-orc/sessions/<id>.jsonl`). 엔진 세션 파일이 아니다.
3. **지휘자는 하이브리드다.** 메시지 1건마다:
   - **라우팅은 지금처럼 결정론 코드**다 — 분류 → 하한선 → 매트릭스 배정. G1(매번 같은 기준)을 모델 판단에 넘기지 않는다.
   - **직접 답** — 하한선에 걸렸거나 분류가 안 되는 메시지(잡담·질문·설명 요청)는 **저비용 모델**(분류 폴백과 같은 계층)이 대화 맥락으로 답한다. 작업처럼 보이면 답 안에서 **"업무 행 Rxx 로 위임할까"를 제안**만 한다 — 임의 배정은 여전히 만들지 않는다 (FR-1).
   - **위임** — 기존 Core 그대로: 배정·비용 → **승인** → 두 슬롯 → 증거.
   - **결과 처리** — primary 출력·reviewer 판정·증거를 대화 기록에 붙이고, 지휘자가 요약과 **다음 제안**(사다리 상향 포함)을 낸다. **다음 위임을 스스로 시작하지 않는다** (D-015 의 비자율 유지).
4. **맥락 전달은 orc 가 한다.** 위임 프롬프트에 세션 요약 + 최근 턴을 싣는다. 엔진 resume(`claude -p --resume`, `codex exec resume`, `cursor-agent -p --resume`)은 **같은 슬롯(같은 엔진·모델)으로 이어지는 후속**에만 최적화로 쓴다. 턴마다 벤더가 바뀌는 제품에서 resume 을 맥락의 진실로 삼으면 교차 벤더 순간 대화가 끊긴다.
5. **승인 게이트는 위임에만 둔다** (G2). 직접 답은 승인 없이 흐르되 비용 한 줄을 찍고 D-030 의 누적 상한을 공유한다 — 말없이 도는 유료 호출은 없다 (D-026).
6. **`/pingpong` 이 GUI 의 기본 진행이 되고, 배정은 턴마다 다시 한다** (D-015 개정 — 세션 고정 배정을 버린다). `/loop`·`/graph` 는 위임 방식의 하나로 채팅에서 고른다.
7. 불변식은 그대로다: 교차 벤더(위임), 증거로 닫기, 결정 로그 2회(**위임에만** — 직접 답은 SPEC §8 의 "하한선에 걸린 결정은 기록 대상이 아니다" 와 같은 자리다).
8. **Core 에 헤드리스 `ConversationSession` 을 둔다** (D-001). 첫 셸은 GUI, CLI·TUI 는 뒤따른다.

**기각**
- *LLM 에이전트가 지휘자* (claude 세션이 orc 를 도구로 부른다) — 가장 유연하지만 G1 이 모델 판단 안에 숨고, 메시지마다 상위 모델 비용이 든다. 라우팅 근거를 결정 로그에 남길 수 없게 된다.
- *엔진 resume 을 맥락의 진실로* — 위 4. 그리고 세션 파일은 엔진 소유라 D-020 처럼 비공식 경로가 된다.
- *폼을 유지하고 직접 답만 붙인다* — 첫 메시지는 살지만 **결과 처리·후속 요청**이 없다. 사용자가 요구한 절반이 빠진다.
- *위임도 승인 없이* — G2 위반. 가장 비싼 경로에서 게이트를 빼는 선택이다.

**Q10 후속 실측** (2026-09-26, claude 2.1.282 · Haiku 4.5 low / codex 0.154.0 · Luna low, 읽기 전용 인자 그대로, git 아닌 임시 폴더 X·Y, 코드워드 `ORC-121410`, n=1)

먼저 코드로 세 경계에 닿는지 봤다. **모델·effort 변경**은 `resumable()` 이 엔진·modelId·effort 가 모두 같을 때만 이으므로 닿지 않는다 — 실측은 가드를 풀 때만 의미가 있고 그것은 결정 4 를 바꾸는 일이라 **실측하지 않았다**. **긴 세션 압축**은 닿는다(같은 슬롯 위임이 이어지면 엔진 쪽 맥락이 쌓인다) — 이번엔 실측하지 않았다(사용자 결정: 다른 cwd 만). **다른 cwd** 는 세션 폴더가 기록 jsonl 의 자리라 폴더 이동·이름 변경으로만 닿는다. 물을 것은 "실패할 때 exit≠0 으로 실패하는가, 조용히 맥락 없는 새 세션을 여는가" 였다.

| 실험 | claude | codex |
|---|---|---|
| 없는 id 로 resume | exit 1, `No conversation found with session ID` · `result.subtype=error_during_execution` · 모델 호출 없음(0 토큰) | exit 1, `no rollout found for thread id` · stdout 0줄 · 모델 호출 없음 |
| X 에서 심고 Y 에서 resume | exit 0, **코드워드 회수**, id 불변, init `cwd` 는 **Y** | exit 0, **코드워드 회수**, id 불변, 세션 기록의 `cwd` 가 X→Y 로 바뀐다 |

결론:
- **조용한 폴백은 없다.** 두 엔진 모두 모르는 id 에 exit 1 로 실패하고, `delegate` 는 실패한 primary 의 세션을 남기지 않으므로 다음 시도는 맥락을 실은 새 실행이다 — SPEC §3.8 의 불변식이 엔진 쪽에서도 성립한다.
- **다른 cwd 에서도 명시적 id 로는 이어진다.** codex 가 cwd 로 거르는 것은 세션 **목록**(`resume` 피커·`--last`)이지 id 지정이 아니다. 새 턴은 **새 cwd 에서** 돈다 — 앞 턴이 본 파일 경로는 옛 폴더를 가리킨다. 그래서 "같은 세션 폴더" 조건은 엔진 제약이 아니라 **의미 보호**로 남긴다. 코드는 바꾸지 않는다 (orc 의 세션 폴더는 기록 자리라 어차피 바뀌지 않는다).
- **(결함 발견) resume 하면 두 엔진 모두 누적값을 보고한다.** claude 는 `result.usage` 는 이번 턴 것이지만 `total_cost_usd`·`modelUsage` 가 세션 누적이다 (2턴 $0.0938752 = 1턴 $0.087634 + 2턴 약 $0.0062, `modelUsage` 출력 173 = 68 + 105). codex 는 `turn.completed.usage` 가 스레드 누적이다 (2턴 input 103,616 = 1턴 40,155 + 세션 로그 `last_token_usage` 63,461). `adapters/stream.ts` 는 claude 의 `total_cost_usd`, codex 의 `turn.completed.usage` 를 그대로 과금하므로 **resume 한 위임은 앞 턴들을 다시 센다** — 체인이 길수록 제곱으로 부푼다. 고치는 방법은 Q14.

비용: claude API 환산 약 $0.094 (구독제, 청구 없음), codex 103,616 토큰.

## D-032 — 토큰 상한은 세션 단위로, 지휘자는 사용자 전역 설정에서 떼어 낸다 (+ codex 캐시 이중 계산 수정)

**배경**
v2.1 실사용(PLAN S10, 2026-09-23)에서 앱 누적 토큰 상한 200만(D-030)이 codex 위임 약 2.5회에 닿았다. 내역을 원시 로그로 쪼개니 원인이 둘이었다.

1. **계측 결함.** `Budget.countTokens` 와 `meteredUsd` 가 `inputTokens + cachedInputTokens` 를 더한다. claude 는 두 값이 따로지만 **codex 의 `input_tokens` 는 캐시를 이미 포함한다** — codex 자신의 세션 기록에서 `total_tokens = input_tokens + output_tokens` 가 정확히 성립한다 (`~/.codex/sessions/…jsonl` 의 `token_count`: 227,815,246 + 164,822 = 227,980,068). 그래서 codex 캐시분 약 81만이 두 번 세어졌다 (203만 중). 금액 환산(metered)도 같은 식이라 부풀어 있었다.
2. **Q13.** 위임된 엔진이 사용자 전역 hook·skills·MCP·CLAUDE.md 를 싣고 뜬다. 지휘자(Haiku)가 사용자를 "전하" 라 부른 것이 그 증거다.

3. **(B1) 지휘자만 격리한다.** 직접 답·요약·분류 폴백(Haiku, claude)은 `--setting-sources project,local --strict-mcp-config --disable-slash-commands` 로 띄운다 — 사용자 hook·설정·MCP·skills 를 싣지 않는다. primary·reviewer 는 **격리하지 않는다**: 사용자의 작업 규칙이 위임 품질의 일부다.

## D-036 — CLI loop 는 실패하면 재시도하고, reviewer 의 FAIL 사유를 다음 사이클에 싣는다 (L2 + L4)

**배경**
CLI 의 loop 는 `recover: () => 'abort'` 라 **1사이클짜리**였다 — PASS 면 goal-reached, FAIL 이면 aborted. `maxIterations`(8) 에 닿을 길이 없었고, 실행 전 "최대 8사이클 · 최악 $…" 안내도 부풀려진 값이었다. 그렇다고 retry 로만 바꾸면 **눈먼 재시도**다: reviewer 프롬프트가 "PASS/FAIL 만 한 줄" 이라 사유가 생성조차 되지 않고, Planner 는 2사이클부터 "직전 사이클의 지적을 반영하라" 만 붙였다. 또 판정 정규식 `/\bPASS\b/i` 는 사유 텍스트 속 PASS 에도 매치된다. 별개로 Evaluator 과금은 추정 금액만 적고 토큰을 세지 않아 D-035 토큰 상한이 reviewer 몫을 빼먹었다.

**결정**
1. **(L2)** CLI loop 는 검증 FAIL 이면 `retry` — `maxIterations`·금액·토큰 상한까지 돈다. Core `runLoop` 의 기본값(recover 미지정 = abort)은 그대로 둔다. 예전 동작은 `--max-iterations 1` 로 똑같이 얻는다 — 그래서 `--recover` 옵션(L3)은 만들지 않는다.
2. **(L4)** loop 의 reviewer 는 once 의 독립 리뷰와 **같은 프롬프트·판정**을 쓴다 (`duo.reviewPrompt`·`parseVerdict`): 누락·반례를 먼저 적고 마지막 줄에 PASS/FAIL. FAIL 이면 그 리뷰 본문이 `Verdict.reason` → `LoopContext.feedback` 으로 다음 사이클의 Planner 에 넘어가고, CLI Planner 는 이를 프롬프트에 싣는다.
3. 판정을 못 읽으면 `unknown` 이고 통과로 봐주지 않는다(fail-closed). 사유 텍스트 속 "PASS" 에 걸리던 `/\bPASS\b/i` 는 버린다. 모드마다 형식을 따로 두지 않는다 — 처음엔 "첫 줄 판정" 새 형식을 적었으나, 이미 검증된 duo 형식이 있어 구현 중 이쪽으로 바꿨다.
4. primary 나 reviewer 의 실행 자체가 실패하면(`ok: false`) 재시도하지 않고 `escalate` 한다. primary 가 죽으면 reviewer 를 부르지 않는다 — 에러 문자열을 채점해 FAIL → 재시도로 상한까지 도는 길을 막는다(구독제에서 실패한 실행은 토큰도 보고하지 않아 토큰 상한이 못 막는다). reviewer 가 죽으면 망가진 엔진에 primary 를 반복해서 태우지 않는다.
5. Evaluator 도 Executor 와 같은 우선순위(actual > metered > estimate)로 과금하고 토큰을 센다. `Verdict.cost` 로 실행 결과를 돌려받는다.

**규모** (추정 — D-035 와 같은 근거, 실측 아님): 1사이클 ≈ 34만 토큰. 기본 상한 200만이면 재시도 포함 약 5~6사이클에서 멈춘다. reviewer 토큰을 세기 시작하므로 이전 추정보다 조금 일찍 멈출 수 있다.

## D-039 — loop 의 primary 실행 실패는 Core 가 채점 없이 사람에게 올린다 (A)

**배경**
D-036 결정 4 의 "primary 가 죽으면 reviewer 를 부르지 않고 escalate" 는 **CLI 클로저에만** 있었다 — `loopExecute` 래퍼가 `ok: false` 를 보고 `evaluate` 가 `skipped: true` 판정을, `recover` 가 `escalate` 를 돌려줬다. Core `runLoop` 는 `run.ok` 를 보지 않는다. 기본 `recover`(없음 = abort)라면 한 사이클로 끝나 안전하지만, retry 를 고른 호출자(앞으로의 TUI/GUI loop)는 에러 문자열을 채점하고 FAIL → 재시도로 `maxIterations` 까지 돌 수 있다. 구독제에서 실패한 실행은 토큰을 보고하지 않아 토큰 상한이 이를 막지 못한다 (D-036).

**결정**
1. `runLoop` 는 primary 실행이 `ok: false` 면 `evaluate`·`critique` 를 부르지 않고, 그 사이클을 `failed` 로 journal 에 남긴 뒤 `escalated` 로 끝낸다. `recover` 가 무엇을 돌려주든 같다.
2. 종료 사유는 새로 만들지 않는다 — 기존 `escalated` 다. journal 검증 문구는 CLI 가 쓰던 `primary 실행 실패 — reviewer 생략: …` 을 그대로 쓴다. CLI 출력은 바뀌지 않는다.
3. CLI 는 primary 쪽 감지를 지우고 reviewer 실패 감지(→ escalate)만 남긴다. reviewer 실행은 호출자의 `evaluate` 안에 있어 Core 가 볼 수 없다.
4. 쓸 곳이 없어진 `Verdict.skipped` 는 지운다.
5. 실패한 primary 에도 Executor 추정 금액을 과금하는 기존 동작은 그대로다 (보수적 방향, 이번 범위 밖).

**기각**
- *B — `run` 을 `evaluate`/`recover` 에 넘기고 호출자가 판단* — 새 호출자마다 같은 가드를 다시 써야 하고, 잊으면 상한까지 돈다.
- *C — 현상 유지 + 문서화* — 토큰 상한이 못 막는 경로를 문서로만 막는다.

**영향**
Core 테스트 "검증에 실패하면 기본은 중단이다" 의 Executor fixture 를 `failingExec` → `fakeExec` 로 바꿨다 — 그 테스트가 보는 것은 검증 FAIL 의 기본 처리이고, 실행 실패는 이제 다른 경로(escalated)다. 호출자가 "실행이 실패해도 재시도" 를 고를 길은 없다 — 요구가 생기면 그때 연다.

**상태** 확정 — 2026-09-24 사용자 결정 (A).

## D-040 — loop 의 검증 명령은 Core 가 돌린다, 읽기 전용이면 돌리지 않고 미실행이라 적는다 (A)

**배경**
D-036 규모 실측(R01, 읽기 전용)에서 reviewer Haiku 는 `claude -p` 권한 거절로 `tsc`·테스트를 돌리지 못한 채, 실패하는 테스트가 있는데도 PASS 했다. 운영 기준 "기존 test 실행" 이 loop 에서는 **아무도 검증하지 않는다**. once 는 `data/verify.json` 선언 + `--verify` 를 Core 가 돌려 증거로 모으지만(SPEC §5) loop 는 돌리지 않았다. 또 읽기 전용이면 primary 의 diff 가 작업 트리에 적용되지 않으므로, 그때 테스트를 돌리면 **원본을 검사한 결과**가 증거처럼 쓰인다.

**결정**
1. CLI loop 는 `--write` 일 때 매 사이클 primary 뒤에 once 와 같은 선언(`verify.json` 행 + `--verify`)을 Core 가 돌린다. 명령·exit·출력 꼬리(1500자)를 reviewer 프롬프트의 "검증 명령 (Core 실행)" 절에 싣는다.
2. 명령이 하나라도 exit ≠ 0 이면 reviewer 판정과 무관하게 FAIL 이다. 실패 명령 출력이 다음 사이클 지적(`Verdict.reason`) 맨 앞에 온다 — 4000자 자르기에 먼저 잘리지 않게.

## D-042 — loop 게이트는 기준선을 먼저 본다: 작업 전부터 빨가면 사람에게 올리고, phase 명령은 게이트에서 뺀다 (B1)

**배경**
D-041 실측에서 사용자는 "타입 오류**만**" 을 요청했지만 R01 의 `npm test` 게이트가 swap 수정을 강제했다 — 테스트가 **작업 전부터** 실패하고 있었기 때문이다. once 는 명령 증거를 exit 와 무관하게 인정하는데(R01 "기존 test 실행 **결과** + exit code"), D-040 은 loop 에서 exit ≠ 0 을 FAIL 로 읽어 "실행" 을 "통과" 로 좁혔다. 기존 실패를 고치는 것이 작업 범위인지 제품은 판단할 수 없다(추론하지 않는다, SPEC §5). 별개로 D-040 은 phase 명령(R05 `before`, R06 `reproduce` — 실패가 정상인 단계)도 exit ≠ 0 이면 FAIL 로 봐서 `--verify before:…` 를 주면 영원히 통과하지 못했다.

**결정**
1. `--write` loop 는 1사이클 **전에** phase 없는 검증 명령(게이트 명령)을 한 번 돌린다 — `기준선 \`cmd\` exit=N`.
2. 기준선이 하나라도 exit ≠ 0 이면 엔진을 띄우지 않고 실패 출력과 함께 사람에게 올린다(exit 1). 기존 실패를 고치는 것까지 범위로 두려면 `--fix-red-baseline` — 그때는 D-040·D-041 그대로 돈다.
3. 기준선이 통과면 이후 실패는 이번 변경이 만든 **회귀**다 — D-040 의 강제 FAIL·D-041 의 reviewer 생략이 범위 문제 없이 성립한다.
4. phase 명령은 매 사이클 돌려 결과를 reviewer 에 싣되, 기준선·강제 FAIL 에서는 뺀다. 표시는 `phase:cmd` 다. — **D-045 가 대체**(phase 를 실행 시점으로 나눈다).
5. `--fix-red-baseline` 은 `--mode loop --write` 밖에서 던진다 — 조용히 무시되는 플래그를 두지 않는다.

**기각**
- *A — 현상 유지* — 사용자 범위를 조용히 넓힌다.
- *B2 — 기준선이 빨가면 게이트를 참고용으로 강등* — D-036 실측에서 Haiku 는 실패하는 테스트를 보고도 PASS 했다. 사실상 게이트가 없어진다.
- *C — `--gate strict|regression` 등 사용자 지정* — 기본값 논쟁이 남고 표면이 가장 넓다.
- *D — "만/only" 같은 문구로 의도 추론* — 추론 금지 원칙(SPEC §5)에 어긋난다.

**영향**
기준선 실행만큼(명령당 최대 300초) 시작이 늦어진다. 원래 빨간 저장소는 매번 `--fix-red-baseline` 이 필요하다. exit 수준이라 "기존 실패 1건 + 새 실패 1건" 은 기준선 실패로만 보인다 — 테스트 이름 비교는 도구마다 형식이 달라 열지 않는다. D-041 실측 조건이라면 엔진 토큰 0 에서 멈췄을 것이다(추론 — 이 변경 뒤 실제 엔진으로 재실행하지 않았다). once 의 outcome 이 실패한 명령을 증거로 인정해 `ok` 로 남을 수 있는 문제는 별개다(미결) → **D-043** 으로 해결 (`contradiction()` → `rework`, once·위임 모두 `outcomeOf`) · exit code 는 **D-044**.

**실행 확인** (2026-09-24, 실제 CLI · 엔진 호출 0회): D-041 실측과 같은 스크래치 저장소에서 `--task R01 --mode loop --run --write --max-iterations 1`. PATH 를 `trap/`(claude·codex·cursor-cli·cursor-agent — 표식을 남기고 exit 99) · `nodeonly/`(node·npm·npx) · `/usr/bin:/bin` 으로만 두고, 실행 전 `command -v` 로 엔진 넷이 전부 trap 인지 확인했다(엔진은 PATH 로만 해석된다 — `resolve.ts`).

## D-043 — 나쁜 결과를 말하는 증거는 `ok` 가 아니라 `rework` 다 (B2)

**배경**
once(CLI)와 위임(GUI·TUI, `delegate.ts`)은 같은 식 `!run.ok ? 'wrong' : report.satisfied ? 'ok' : 'unverified'` 로 결정 로그 2차 outcome 을 정했다. 두 겹의 결함이 있었다.
1. `validate` 는 명령 증거의 exit 가 정수인지만 본다 — `npm test` exit=1 도 R01 "기존 test 실행 결과" 로 충족돼 `ok` 가 됐다. R05·R06 은 SPEC §5 표가 "수정 전 **실패** / 수정 후 **통과**" 인데 코드는 phase 존재만 봤다.
2. reviewer 판정이 outcome 에 들지 않았다 — R11 외 행은 review 증거를 요구하지 않아 reviewer FAIL 이어도 `ok`, R11 도 FAIL 리뷰를 "독립 리뷰 결과" 로 충족했다.
결정 로그는 `/delegation-router` 의 하향 판단이 읽는다 — 거짓 `ok` 는 "내려도 됐다" 는 근거를 부풀린다(추론 — 라우터 집계는 이 저장소 밖이다). `Outcome` 에 정의만 있고 쓰지 않던 `rework` 가 정확히 이 상태다.

**결정**
1. `evidence.ts` 에 `contradiction(e)` — 모양 검사(`validate`)와 별개로 증거가 **나쁜 결과**를 말하는지 본다. phase 없는 명령과 `after`·`fix`·`regress`(및 그 밖의 phase)는 exit 0 을, `FAILING_PHASES`(`before`·`reproduce`)는 exit ≠ 0 을 기대한다. reviewer `fail` 도 나쁜 결과다. `unknown` 은 증거가 생기지 않으므로 판정에 쓰지 않는다.
2. `collect` 는 `contradictions` 를 돌려주고, 있으면 요약이 `검증 결과 완료가 아니다 — …` 다. 실패한 증거를 **거절하지 않는다** — R05 `before` 처럼 실패가 증거인 단계가 있다.
3. `outcomeOf(runOk, report)`: `wrong`(실행 실패) → `rework`(나쁜 결과) → `ok`(증거 충족) → `unverified`. CLI once 와 `delegate.ts` 가 이것 하나를 쓴다.
4. outcome 타입을 `SettledOutcome`(`ok|rework|unverified|wrong`)으로 모은다 — delegate·conductor·transcript·GUI service. 다음 제안(`nextSuggestion`)은 `rework` 에도 사다리를 제안한다(`ok` 가 아니므로).
5. CLI once 증거 출력에 `✗ 불일치: …` 줄, 2차 `verified` 에 `불일치: …` 를 남긴다. 위임 journal 의 검증 줄은 불일치가 있을 때도 채운다.

**기각**
- *A — 현상 유지 + `ok` 재정의* — `ok` 가 성공으로 읽히는 한 통계가 오염된다.
- *B1 — exit 만 반영* — reviewer FAIL 을 계속 무시한다. loop(D-036)는 FAIL 을 완료로 보지 않는다.
- *C — 실패한 명령을 증거에서 거절* — "증거 없음" 과 "실패의 증거" 가 섞이고, phase 를 모르면 R05·R06 이 영영 충족되지 않는다.

**영향**

## D-045 — loop 는 phase 를 실행 시점으로 나눈다: before·reproduce 는 기준선, 나머지는 매 사이클 게이트 (B)

**배경**
D-042 는 loop 의 phase 명령을 전부 게이트에서 빼고 결과만 reviewer 에 실었다 — `--verify after:npm test` 가 실패해도 사이클이 FAIL 이 되지 않아 약한 reviewer 가 판정했다. D-043 은 once 에 phase 별 기대 exit 표(`FAILING_PHASES`·`contradiction()`)를 뒀다. 그런데 이 표를 loop 의 매 사이클에 그대로 대면 **틀린다**: 사이클 검증은 primary 가 **변경한 뒤**의 트리에서 도는데, `before`·`reproduce` 는 의미상 **변경 전**의 사실이다 — 버그를 제대로 고친 사이클에서 통과하는 것이 정상인데 "실패해야 하는데 exit 0" 으로 FAIL 이 된다. loop 에는 변경 전 시점이 이미 하나 있다 — D-042 의 기준선.

**결정**
1. `before`·`reproduce`(`FAILING_PHASES`)는 **기준선에서 한 번** 돈다. exit ≠ 0 을 기대하고, 결과를 매 사이클 reviewer 프롬프트에 `(기준선 — 변경 전)` 으로 싣는다. 사이클마다 다시 돌리지 않는다.
2. 기준선에서 그것이 exit 0 이면 "재현되지 않는다" 로 엔진을 띄우지 않고 사람에게 올린다(exit 1). **우회 플래그는 두지 않는다** — `--fix-red-baseline` 으로도 넘어가지 않는다. 재현되지 않는 버그를 고치라고 시키는 것은 추측이다. 재현 명령을 고치는 것이 답이다.
3. phase 없는 명령과 그 밖의 phase(`after`·`fix`·`regress` 등)는 **매 사이클 게이트**다 — exit 0 을 기대하고 아니면 강제 FAIL, reviewer 생략(D-040·D-041).
4. 기준선의 "이미 빨갛다" 확인(D-042)은 phase 없는 명령만 본다 — `after`·`fix`·`regress` 는 변경 전에 실패하는 것이 정상이다.
5. 기대 exit 판단은 D-043 의 `contradiction()` 하나다. once 와 loop 가 같은 표를 쓰고, 표를 **어느 시점에 대는지**만 loop 가 정한다.
6. D-042 결정 4("phase 명령은 게이트에서 뺀다")를 대체한다.

**기각**
- *A — 현상 유지* — `after` 실패가 게이트에 걸리지 않고 once(D-043)와 기준이 갈린다.
- *C — 표를 매 사이클 그대로* — 위 이유로 제대로 고친 사이클이 FAIL 이 된다.
- *D — `after` 등만 게이트로* — 재현 확인이 빠지고 `before` 가 변경 후 트리에서 의미 없이 돈다.
- *재현 안 됨 우회 플래그* — 사용자 결정으로 두지 않는다(결정 2).

**영향**
`--verify after:…` 로 쓰던 실행은 실패하면 이제 FAIL → 재시도다(의도). `before:…` 는 기준선 줄에 나오고 사이클마다 돌지 않는다. 저장소의 `verify.json` 선언에는 phase 가 없어 기본 경로는 바뀌지 않는다. 테스트: D-042 phase 테스트를 D-045 기대(기준선에서 재현·reviewer 에 기준선 결과)로 바꾸고, 재현 안 됨(플래그로도 못 넘김)·`after` 게이트 2건을 더했다.

**상태** 확정 — 2026-09-24 사용자 결정 (B, 재현 안 됨 우회 없음).

## D-046 — 돌지 못한 검증 명령(126·127·시그널·시간 초과)은 테스트 실패가 아니라 환경 문제로 올린다 (B2)

**배경**
D-042 실행 확인에서 격리 설정 실수(PATH 에 `/bin` 없음 → exit 127)도 "작업 전부터 검증 명령이 실패한다" 로 나와, 원인은 출력 꼬리를 읽어야 알았다. 옵션을 정리하며 두 결함을 더 찾았다(코드 경로로 확인, 실행 재현은 테스트로).
1. D-045 의 재현 판정은 `before`·`reproduce` 에 "exit ≠ 0" 만 기대해, **없는 명령의 127 을 "재현됨"** 으로 읽고 엔진을 띄운다. once(D-043)도 같은 127 을 유효한 "수정 전 실패 로그" 로 쳤다.
2. `after:` 등은 D-045 이후 기준선에서 돌지 않는다 — 사이클 중 127 이면 FAIL → 그 출력이 지적이 되어 primary 를 **재시도**한다. primary 는 PATH 를 고칠 수 없으니 상한까지 태운다(D-039 와 같은 종류의 낭비).

**결정**
1. `evidence.ts` 에 `notRun(exitCode)` — `sh` 규약 126(실행 불가)·127(명령 없음)과 `runCommand` 의 -1(시그널·시간 초과)을 "돌지 못했다" 로 가른다. 추론이 아니라 규약이다.
2. `contradiction()` 은 돌지 못한 명령을 phase 와 무관하게 나쁜 결과로 본다 — `\`before:x\` 가 실행되지 못했다 (exit 127 — …)`. once·loop 가 같이 쓴다.
3. loop 기준선: 돌지 못한 명령이 하나라도 있으면 "검증 명령을 실행할 수 없다 — 테스트 실패가 아니라 환경 문제다" 로 엔진 없이 올린다(exit 1). 재현 안 됨·기준선 빨강보다 먼저 보고, `--fix-red-baseline` 으로 넘어가지 않는다 — 모델도 플래그도 환경을 고치지 못한다.
4. loop 사이클: 돌지 못한 명령이 있으면 reviewer 를 생략하고(`reviewerSkipped`) `recover` 가 **escalate** 한다 — `reviewerBroken` 과 같은 방식. 재시도하지 않는다.

**기각**
- *A — 현상 유지* — 원인이 출력 꼬리에만 있고, 위 두 결함이 남는다.
- *B1 — 문구만* — 사이클 중 재시도 낭비가 남는다.
- *C — 출력 패턴 파싱*(`command not found`·`MODULE_NOT_FOUND`) — 도구마다 문구가 달라 추론이 된다(SPEC §5).
- *D — 사전 `command -v`* — 127 과 같은 정보이고 셸 구문(`n=0; …`, 파이프)에서 틀린다.

**영향**
도구가 exit 1 로 내는 환경 오류(npm `MODULE_NOT_FOUND`)는 여전히 "돌았고 실패했다" 로 보인다 — exit 만으로는 못 가른다. 테스트가 스스로 127 을 내는 드문 경우도 사람에게 올라간다(보수적 방향). once 의 127 은 이제 `rework` 로 남고 요약에 "실행되지 못했다" 가 나온다.

**상태** 확정 — 2026-09-24 사용자 결정 (B2).

## D-047 — 선언된 기존 테스트는 줄 추가만 허용한다, 약해지면 완료가 아니다 (B)

**배경**
D-040 부터 loop 는 검증 명령(`npm test`)이 통과해야 PASS 다 — primary 에게 **기존 테스트를 고치거나 지워 게이트를 통과시킬** 유인이 생긴다(reward hacking). 게이트는 exit 만 보고 reviewer(Haiku)는 약해 이를 막는 장치가 없었다. D-036 critique 실측에서는 primary 가 R01("기존 test 만 실행")인데도 테스트를 **추가**했다 — 이쪽은 무해하다. R03(acceptance test 를 먼저 작성)·R06(회귀)은 테스트 추가가 운영 기준에 맞으므로 "테스트 파일을 건드리지 마라" 는 전역 규칙이 될 수 없다.

**결정**
1. 프로젝트가 `verify.json` 의 `tests`(cwd 기준 glob)로 기존 테스트를 **선언**한다. 선언이 없으면 보지 않는다 — 테스트 위치를 추측하지 않는다(`verify.json` 의 기존 원칙). 이 저장소는 `src/**/__tests__/**/*.ts`.
2. 작업 전 선언된 파일의 내용을 스냅샷한다 — loop 는 기준선 뒤·1사이클 전, once(CLI)는 `--write` 일 때 primary 전, 위임(`delegate.ts`, GUI·TUI)은 primary 전.
3. 판정은 기계적이다: 원래 줄이 새 내용 안에 **순서대로 전부** 있으면 추가(허용·기록), 아니면 약화, 파일이 없어졌으면 약화. 새 파일은 추가. 새 증거 종류 `test-files`(`weakened`·`added`)로 담고 `contradiction()` 이 약화를 나쁜 결과로 본다 — once·위임은 `rework`(exit 1, D-044).
4. loop: 약화면 reviewer 를 생략하고 FAIL, 지적 맨 앞에 "기존 테스트를 약하게 만들지 말고 코드를 고쳐라 (줄 추가만 허용)" — 모델이 고칠 수 있는 문제라 escalate 가 아니라 재시도다. 비교 기준은 언제나 작업 전 스냅샷이다(사이클 사이에 자기가 더한 줄을 지우는 것은 괜찮다).
5. 실행 전 안내에 선언 여부를 찍는다 — "줄 추가만 허용" 또는 "선언이 없다 — 약화를 막지 않는다".
6. R01 에 "추가도 금지"(C)는 얹지 않는다 — "기존 test 만 **실행**" 이 추가 금지인지는 해석 문제다.

**기각**
- *A — 현상 유지* — 약화를 막는 장치가 없다.
- *C — 행별 엄격 금지* — 해석 논쟁과 행별 설정 표면이 남고 약화 방지는 따로 필요하다.
- *D — 표시만* — 약화를 사람이 매번 읽어야 한다.
- *E — 엔진 쓰기 권한으로 테스트 경로 차단* — 엔진마다 경로 단위 제어가 없거나 다르고(codex 는 `workspace-write` 뿐), R03 을 막는다.

**영향**
줄 단위라 `it(` → `it.skip(` 처럼 줄을 **바꾸는** 약화는 잡지만, 원래 줄을 모두 남긴 채 사이에 `return;` 을 끼우는 약화는 추가로 보여 통과한다 — reviewer·사람 몫이다. 정당한 테스트 수정(틀린 기대값 교정)도 막혀 rework·재시도가 된다 — 그때는 사람이 직접 고친다. 선언 경로의 파일을 매 실행 읽는다(이 저장소 약 30개). `verify.json` 은 hs-orc 설치본의 것이라 다른 프로젝트에서 돌리면 그 프로젝트가 자기 `tests` 를 적어야 한다(`$declared` 와 같다).

**실제 엔진 확인** (2026-09-25, n=1): 스크래치 저장소 green, `HS_ORC_VERIFY_CONFIG` 로 `{"R01":["npm test"],"tests":["*.test.ts"]}`, `"clamp.ts 를 바꿔라: min > max 이면 두 값을 바꾸지 말고 RangeError 를 던진다." --task R01 --mode loop --run --write --max-iterations 2`. 과제가 **기존 테스트의 기대값을 바꿔야만 끝나도록**(정당한 테스트 수정) 골랐다 — 실제 primary 는 보통 테스트를 약화하지 않아 사건이 안 생기므로. primary codex Luna·medium, reviewer Haiku·low 모두 진짜, shim 이 codex 호출마다 `git diff` 를 떴다.

## D-048 — `--write` loop 는 의존성이 없으면 검증 명령이 있을 때 엔진 전에 멈춘다 (F)

**배경**

**결정**
1. `buildContext` 가 버린 양 `{ turns, chars }` 를 돌려주고, 세션은 잘렸을 때만 그 맥락을 받은 `direct`·`result` 기록에 `cut` 으로 남긴다. resume 으로 엔진이 가진 턴(`after` 이전)은 버린 것으로 세지 않는다.
2. **여는 기준:** `cut` 이 있는 턴 뒤에 (a) 사용자가 잘려 나간 내용을 다시 설명했거나 (b) 지휘자·primary 가 잘려 나간 내용을 몰라 답이 어긋난 사례가 **1건이라도 확인되면** rolling 요약을 설계한다. 판정은 사람이 기록을 읽고 한다 — 자동 판정은 없다.
3. 확인 방법: 세션 폴더에서 `grep -l '"cut"' .hs-orc/sessions/*.jsonl` 로 잘린 세션을 찾고, 그 뒤 턴을 읽는다. `cut` 이 한 번도 없으면 기준을 볼 필요도 없다.

**기각**
- *지금 실제 엔진으로 실측* (1턴에 코드워드, 8턴에 되묻기) — 6턴 밖은 설계상 싣지 않으므로 "잊는다" 는 결과가 정해져 있다. 새로 알게 되는 것은 없고 사용량만 든다. 필요한 것은 실사용에서 6턴 밖을 참조하는 빈도다.
- *기준만 적고 계측 없음* — 기록은 오프라인 재계산으로 사후 확인할 수 있지만, 한도 값이 바뀌면 당시 무엇이 잘렸는지 재현하려면 당시 limits 를 알아야 한다. 기록 시점에 남기는 편이 싸다.
- *잘림 횟수 N회 이상이면 연다* — 잘림 자체는 해가 아니다(6턴 전 잡담은 버려도 된다). 연다/안 연다를 가르는 것은 잃은 맥락이 필요했는지다.

**영향**
- 기록 형식에 선택 필드 하나(`cut?`)가 는다. 기존 기록은 그대로 읽힌다(`v: 1` 유지).
- 판정이 사람 몫이라 아무도 기록을 안 읽으면 기준이 돌지 않는다 — 긴 세션을 쓴 뒤 한 번 보는 것을 전제로 한다.
- 화면에는 아직 표시하지 않는다. 필요하면 별도로 정한다.

**상태** 확정 — 2026-09-25 사용자 결정 (계측 + 기준 명문화).

## D-054 — 세션 Budget 은 대화 기록의 `spend` 줄로 영속한다 (D-032 A2 보완)

**배경**
D-032 A2 로 토큰 상한이 세션 단위가 됐지만 세션 `Budget` 은 GuiService 의 메모리 Map 에만 있었다. 앱을 다시 켜고 같은 세션을 열면 0 부터 센다(PLAN S10 후속). 기록에는 `direct` 의 비용 문자열만 있고 토큰은 없어 되살릴 재료가 없었다.
영향 재평가: 새 세션도 0 부터 세고(A2), 대화 세션은 위임마다 승인을 받으므로 재시작이 **상한을 넘는 우회**는 아니다. 실제 피해는 다시 연 세션의 누적 표시가 0 이라 이 세션이 얼마를 썼는지 잘못 보여주는 것이다.

**결정**
1. 직접 답(`answer`)·위임(`approve` — 두 슬롯 + 요약)이 끝날 때, 그 사이 `Budget` 에 쌓인 증분을 기록에 `spend` 한 줄로 append 한다: `{ kind: 'spend', charges, tokens, unreported }`. 쌓인 게 없으면 남기지 않는다.
2. `spend` 는 결과·요약·오류 **뒤에** 붙는다 — `interrupted` 는 마지막 줄이 승인인지로 끊김을 판정하므로 그 앞에 끼면 안 된다.
3. GuiService 가 세션 Budget 을 **처음 만들 때**(앱 실행 중 첫 열기) 기록의 `spend` 를 재생한다. 같은 실행 안에서 다시 열면 Map 의 것을 그대로 쓴다 — 두 번 재생하지 않는다.
4. 화면(`SessionView.records`)에는 `spend` 를 싣지 않는다. 화면은 마지막 기록으로 버튼(SUGGEST 위임 등)을 고른다.

**기각**
- *영속하지 않음을 명문화* — 비용 0 이지만 다시 연 세션의 누적 표시가 거짓으로 남는다.
- *별도 `<id>.budget.json` 스냅숏* — 진실이 둘(기록·스냅숏)이 되고, 덮어쓰기라 append-only 원칙(D-031)에서 벗어난다.
- *기존 `direct`·`result`·`summary` 에 필드로 싣기* — 위임 한 번의 과금이 여러 줄(primary·reviewer·요약)에 흩어지고, 실패 경로(`error` 만 남는 경우)의 과금을 놓친다.

**영향**
- 기록 형식에 `kind` 하나가 는다(`v: 1` 유지). 이 버전 전의 기록은 `spend` 가 없어 여전히 0 부터 센다.
- 위임 도중 앱이 끊기면 그 위임의 과금은 기록되지 않는다(끝날 때 한 번 쓰므로) — 끊김은 `interrupted` 배너로 따로 보인다.

**상태** 확정 — 2026-09-26 사용자 결정 (기록에 과금을 남겨 재생).

## D-055 — git 이 아닌 project 폴더에서 codex 는 읽기 전용 위임만 돈다

**배경**
`codex exec` 는 git 저장소 밖에서 `--skip-git-repo-check` 없이 실행을 거부한다(2026-09-23 실측). hs-orc 는 이 인자(`nonGitArgv`)를 **스크래치 세션에만** 붙였다 — 쓰기를 켤 수 없는 자리라서다. 그래서 git 이 아닌 project 폴더에서 codex 행으로 위임하면 승인 뒤 오류 줄만 남았다(PLAN S10 후속). claude·cursor 는 이 제약이 없다.
그 뒤 D-051 로 읽기 전용 codex 실행에 `sandbox_mode="read-only"` 를 명시하게 됐다 — git 이 없어도 읽기 전용 실행은 스크래치와 같은 조건이다.

**결정**
1. git 이 아닌 project 폴더에서 **쓰기를 켜지 않은** 실행(위임·지휘자)에는 `--skip-git-repo-check` 를 붙인다. 판정은 `skipGitCheck(kind, inGit, write)` — 스크래치는 언제나, project 는 `repoRoot(dir) === null && !write` 일 때.
2. 쓰기를 켠 위임은 지금처럼 인자를 붙이지 않는다 — codex 가 거절하고 오류 줄이 남는다. 쓰기를 되돌릴 git 이 없고, 바뀐 파일 증거(`changedFiles`)도 `git status` 로 모으기 때문이다.
3. 스크래치의 쓰기+git 밖 조합은 여전히 `resolve` 에서 던진다(방어선 유지).

**기각**
- *거절 유지 + 배정 카드에 사유 표시* — 헛된 승인은 막지만 읽기 전용 위임까지 막을 근거가 D-051 이후 사라졌다.
- *쓰기까지 허용* — 되돌릴 수단과 변경 증거가 모두 없다.
- *문서만(의도된 제약)* — 위와 같은 이유로 제약이 필요 이상이다.

**영향**
- git 이 아닌 project 의 쓰기 켠 codex 위임은 여전히 실패한다 — 승인 전에 알리지 않는다(필요하면 별도로 정한다).
- 실제 codex 실행으로는 확인하지 않았다. `--skip-git-repo-check` 동작은 D-031 Q10(스크래치, git 아님)에서 실측됐고, 이번 변경은 그 인자를 붙이는 조건만 넓힌다.

**상태** 확정 — 2026-09-26 사용자 결정 (읽기 전용만 허용).

## D-057 — resume 한 실행은 직전 원본 보고를 빼서 과금한다 (Q14)

**배경**
D-031 Q10 후속 실측(2026-09-26)에서 resume 한 실행의 보고가 **세션 누적**으로 드러났다 — claude 는 `total_cost_usd`(토큰 `usage` 는 이번 턴 몫), codex 는 `turn.completed.usage`. 어댑터는 그것을 이번 실행 몫으로 과금했으므로 같은 슬롯 후속이 이어질수록 앞 턴이 거듭 더해져 Budget 이 제곱으로 부풀고, 상한(D-017·D-030)에 일찍 닿았다.

**결정**
1. **무엇이 누적인지는 엔진 선언이다.** `engines.json` 의 `resume.cumulative` — claude `["cost"]`, codex `["usage"]`. cursor 는 실측이 없어 선언하지 않는다(= 빼지 않는다).
2. **기준은 orc 의 기록에 남긴다.** 실행기가 엔진의 원본 보고를 `SlotRun.reported` 로 돌려주고, `delegate` 가 그것을 `engineSession.reported` 로 대화 기록에 싣는다. 다음 resume 은 그 값을 `baseline` 으로 받는다 — 세션을 다시 열어도(D-054) 그대로다.
3. **실행기가 뺀다** (`sinceBaseline`). 선언된 칸만, 빼서 음수가 나오면 그 칸은 원본을 센다. 기준이 없으면(이 결정 전 기록, 엔진이 보고를 안 준 실행) 원본을 센다 — **적게 세면 상한이 거짓이 되고, 많이 세면 일찍 멈출 뿐이다.**
4. codex 의 토큰 정규화(D-032, 입력에서 캐시 빼기)는 선형이라 누적에서 빼기 전·후 어느 쪽에서 해도 같다 — 정규화된 값끼리 뺀다.

**기각**
- *엔진 세션 로그를 읽는다* (codex `last_token_usage`) — D-020 과 같은 비공식 경로, 형식이 예고 없이 바뀐다.
- *claude 금액을 `usage` × 단가로 계산한다* — 엔진이 주는 실제 금액을 버리고 추정으로 바꾼다. 1h 캐시 쓰기 같은 요율 차이를 단가표가 따라가야 한다.
- *기준이 없으면 resume 하지 않는다* — 한 번 과대 계상을 막으려고 맥락 최적화를 끈다. 과대 계상은 안전한 쪽이다.

**검증**
실측 원본 수치로 두 엔진 경로를 테스트한다 (codex 는 세션 로그의 `last_token_usage` 63,461/39,680/33 과 일치). 세션 테스트는 두 번째 primary 가 첫 실행의 원본 보고를 기준으로 받는지 본다. **미검증**: 실제 엔진으로 resume 체인을 돌려 Budget 을 대조하지 않았다. cursor 가 누적인지 모른다.

## D-058 — 엔진이 압축하면 결과 기록에 남긴다 (Q15)

**배경**
resume 체인(D-031 결정 4)에서 orc 는 이을 때 그 실행 **이후**의 대화만 싣는다 — 앞 맥락은 엔진이 가진다고 믿는다. 엔진이 압축하면 그 믿음이 조용히 깨진다. 2026-09-26 압축 탐색(D-031 Q10 후속)에서 claude 가 `system`·`compact_boundary`(`compact_metadata.trigger·pre_tokens·post_tokens`)를 흘리는 것을 확인했다.

**결정**
1. 어댑터가 claude 형식 스트림의 `compact_boundary` 를 `compact` 이벤트로 읽는다. 토큰 칸은 엔진이 줄 때만 싣고, 메타데이터가 없어도 압축 사실은 남긴다(`trigger: "unknown"`).
2. `RunResult.compactions` → `SlotRun` → `Delegated` → 대화 기록 `result.compacted` 로 흐른다. primary 만 — reviewer 는 resume 하지 않는다.
3. CLI `chat` 은 결과 아래 `압축` 줄을 찍는다. **동작은 바꾸지 않는다** — 압축된 세션도 계속 잇는다. 기록은 맥락 신뢰도를 판단할 재료다(D-053 의 `cut` 과 같은 자리).

**기각**
- *압축된 세션은 다음부터 잇지 않는다* — 압축 뒤 맥락이 orc 의 최근 N턴 자르기보다 나쁘다는 근거가 없다. 잇기를 끊으면 캐시·맥락 비용만 는다.
- *두지 않는다* — resume 체인의 맥락이 요약으로 바뀐 사실을 사용자와 orc 가 모두 모른다.

**검증** 실측 줄로 파싱 테스트, 세션 테스트(기록에 남는지 — 배선을 끊으면 실패함을 확인), chat 렌더 테스트. **미검증**: codex·cursor 의 압축 신호(codex `exec` 스트림에서 본 적 없다). GUI 는 `cut` 과 마찬가지로 아직 그리지 않는다.

**자동 압축 실측** (2026-09-26, claude 2.1.283 · Haiku low, 스크래치, n=1 · 사용자 승인): 1턴에 코드워드 + 번호 붙인 사실 20개를 심고, 2턴을 `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE=20` 으로 resume 해 코드워드와 "사실 13 의 사물함 코드" 를 되물었다. 임계값을 낮춘 것은 200k 를 채우지 않으려는 것이다 — 변수는 바이너리 문자열로 찾았고, 이름대로 동작함을 이 실측이 보였다.
- 2턴 안에서 **자동 압축이 일어났다**: `compact_boundary` 의 `compact_metadata` = `{ trigger: "auto", pre_tokens: 46382, post_tokens: 9763, cumulative_dropped_tokens: 36619, … , preserved_segment: {…} }`. 캡처한 스트림을 `parseLine` 에 그대로 넣으면 `compact` 이벤트가 `{ trigger: "auto", preTokens: 46382, postTokens: 9763 }` 로 나오고 `unparsed` 는 0 이다 — 이 결정의 경로가 실제 자동 압축 줄에서 동작한다.
- **압축 뒤 답: `CODEWORD=ORC-102924 FACT13=NONE`.** 코드워드는 남았고 **사실 13(`5978-6dd1fe`)은 잃었다.** 요약은 "기억하라" 고 한 대표 값은 싣지만 목록의 세부는 버린다. 같은 대화를 orc 의 최근 N턴 맥락(D-053)으로 보냈다면 1턴 본문이 그대로 실렸을 것이다(추론 — 사실 목록이 약 1.5k 자라 글자 상한 안이다).
- 결정 3(압축돼도 잇는다)과 기각한 "*압축된 세션은 다음부터 잇지 않는다*" 의 근거("압축이 orc 의 자르기보다 나쁘다는 근거가 없다")가 **n=1 로 흔들린다.** 정책을 바꿀지는 Q16.
- 2.1.283 부터 `result` 뒤에 `system`·`task_summary` 줄이 하나 더 온다. 파서는 줄마다 읽으므로 영향이 없다.
